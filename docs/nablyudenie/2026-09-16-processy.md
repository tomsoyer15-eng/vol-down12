# Наблюдение 16.09.2026 — накопление процессов шлюза и требование перезагрузки

Повод: заказчик заметил в приветствии VPS строку `*** System restart required ***`.
Проверка причины вывела на второе, независимое обстоятельство — накопление зависших
процессов. Код не менялся. Запись по правилу пилота §7 (сначала фиксация, не чинить на ходу).

## 1. Перезагрузка требуется, причина обычная

```
cat /var/run/reboot-required.pkgs
  linux-image-6.8.0-138-generic / linux-base / linux-image-6.8.0-139-generic / libc6
uname -r            -> 6.8.0-137-generic
ls /boot/vmlinuz-*  -> 6.8.0-137-generic, 6.8.0-139-generic
uptime              -> up 36 days, 21:44
```
Работающее ядро 137, установленное 139, плюс обновлённая libc6. Это штатный apt-апдейт,
не признак сбоя.

четырёх оставили после себя висящий процесс.**

## 3. Последствие: торговля НЕ страдает

Во все четыре дня контур отработал штатно и это проверяемо по журналу:
```
2026-09-14 16:45:04 шлюз не отвечает — запускаю
2026-09-14 16:45:25 шлюз поднят, API отвечает      (21 секунда)
2026-09-14 16:46:03 торговля 2026-09-14: ок
```
Те же три строки с той же секундной раскладкой — 03.09, 08.09, 10.09. Отметки
`traded-*` и `closed-*` за все четыре дня на месте. То есть висящий процесс не держит
ни книгу, ни замок (`flock`, а не каталог — замок умирает вместе с процессом и с машиной),
и не мешает следующему тику.

Расходуется только память: ~1,6 ГБ RSS и 2 ГБ свопа за 13 дней, темп примерно один
зависший тик и один шлюз на 2–4 дня.

## 4. Класс

**Не BLOCKER и не MATERIAL на сегодня.** Проверено по списку A–F режима пилота:
неправильной позиции или заявки нет (A), контроль над позицией брокера не теряется (B),
торговля после стоп-состояния не продолжается (C), остановки контура не было и свободной
памяти 4,2 ГБ (D), ошибки данных/сигнала/ролла/маржи нет (E), сборке и выпуску не мешает (F).

Направление, однако, одностороннее: память только убывает. Если накопление продолжится и
доступная память кончится, это станет классом D — необоснованная остановка контура.
Поэтому: **запись, счётчик, перепроверка**, а не правка кода.

## 5. Что делать (и чего НЕ делать)

Делать: **перезагрузить машину** — она и так требует перезагрузки ради ядра, и та же
перезагрузка снимает все четыре зависших тика и все шесть JVM разом, без единой строки
кода. Окно безопасное: после замыкания и до торговой сессии, то есть примерно
10:00–16:00 по машине (сессия на Е — 16:45–17:45, замыкание — после полуночи).
Возврат автоматический: `cron.service` включён в `multi-user.target.wants`, шлюз поднимает
`ensure_gw` на первом же тике (доказано четыре раза выше — 21 секунда).

НЕ делать: не трогать `autopilot.sh`. Режим пилота §3 запрещает её правку без
воспроизведённого BLOCKER/MATERIAL, а здесь его нет. Механизм зависания лежит в связке
`ensure_gw` -> `start.sh` -> `ibcstart.sh` -> JVM, но разбирать её сейчас означало бы
открыть ровно тот аудит оболочки, который закрыт решением заказчика.

Перепроверить после перезагрузки: счётчик зависших тиков должен стать 0, число JVM — 1.
Дальше смотреть тот же счётчик раз в неделю; если за месяц он снова дойдёт до четырёх при
свободной памяти менее ~2 ГБ, карточка переоткрывается уже как MATERIAL с воспроизведением.
