# Рецензия сорок второго круга ред. 33 (gpt-5.6-sol, pro+max)

### P0 — неверная позиция / поставка

1. **`live/daily.py::step`, `leg_roll_due`, `target_tag` — первый вход в день ролла открывает уходящую серию.**

   При боевом `Market.holidays != ()` и пустой ноге:

   ```python
   leg_roll_due(None, m) == False
   roll_now_a = roll_now_b = False
   target_tag(None, 2026-08-26, False, roll_passed=False) == 'U26'
   ```

   То есть 26.08.2026 новая книга покупает U26 вместо Z26. На следующий день возникает полный лишний ролл; при пропуске следующей сессии позиция остаётся у поставки.

   **Ложное доказательство:** проверки «первого входа» в `contour_test.py` создают `Market` без `holidays`, поэтому идут по противоположной ветке `not _have_hol`. Зонд «обе ноги уже свежие» начинается с ненулевой Z26 и случай `held is None` не достигает.

2. **`live/daily.py::run_session` — доказуемо откаченный ролл невозможно продолжить следующей биржевой сессией.**

   Обработчик `RollGap(provable=True)` сохраняет только:

   ```python
   replace(book, roll_pending=_legs)
   ```

   но не переносит `last_session` на текущую дату. Если 26.08 ролл не начался из-за закрывшегося окна, книга остаётся с `last_session=2026-08-25`. На 27.08 код раньше `step()` проверяет предыдущую сессию, ожидает 26.08 и отказывает:

   ```python
   book.last_session != prev_session(market.date)
   ```

   `roll_pending` остаётся недостижимым. Обещание «перенос выполнится следующей сессией» ложно; старая серия требует ручной правки состояния.

   **Ложное доказательство:** ролловые траектории в `invariants.py::run_roll` вызывают `step()` напрямую и полностью обходят календарный guard `run_session`.

3. **`live/daily.py::run_session` — первая штатная сессия без заявок создаёт книгу без журнала и запирает контур.**

   Для `dec.trade == False` код не пишет ни строк исполнения, ни нулевой `ИТОГ`, но всё равно сохраняет книгу с новым `session_no` и `last_session`.

   Последствия:

   - первое замыкание доходит до `worm_anchor._anchor_body`, не находит `journal-F.csv`/`journal-E.csv` и поднимает постоянный `ALARM-backup`;
   - если WORM обойти, первая будущая сессия с заявками откажет: «журнал пуст, а книга несёт сессию №…».

   Это достижимо при первом запуске с обеими выключенными ногами. Нормальный первый вход позже никогда не состоится.

   **Ложное доказательство:** сессионные фикстуры заранее сеют журнал `ИТОГ` даже для искусственно созданных книг. Живой путь «пустая книга → успешная сессия без ордеров → первая последующая сделка» не исполняется.

4. **`live/ib_broker.py::IBBroker.preview` — аварийный выход Е→Ф по-прежнему заперт маржинальным стрессом.**

   При текущем запасе, например, `1.20×` и отрицательных `initMarginChange` по всем целевым заявкам:

   ```python
   _need < 0
   _pos_need == 0
   _worst == 0
   return _c >= O3E_MIN   # False при 1.20
   ```

   Именно при пробитом О-3-Е выход будет трижды `POSTPONED`, затем `ABORT`; маржинальная книга Е останется на месте. Удаление `FullInitMarginReq` эту ветку не открыло. Флаг `emergency` в `preview` вообще не передаётся.

   **Ложное доказательство:** `ib_stub.StubIB.whatIfOrder` умеет только положительную маржу, «тесно» и пустой ответ. Ни отрицательная сумма, ни смешанные знаки, ни аварийный выход при `cushion < 1.40` не достигаются ни `SAME_API`, ни мутациями.

5. **`live/ib_broker.py::IBBroker.unit_ref`, `gross` — «один момент» не обеспечен.**

   `at_close=True` лишь переключает каждый инструмент на его последнее закрытие, но даты выбрасываются. Более того, `closes(..., expected_prev=None)` допускает бар возрастом до пяти дней. В одном `gross()` могут смешаться:

   - пятничный CSPX;
   - понедельничный CBU0/ES;
   - другая дата TNX для ZN.

   Все числа будут конечны и пройдут полосы, но сравнение с `CLOSE_CAP=2.00` относится к несуществующей книге во времени. Движение между датами способно дать ложный `COMPLETE` выше фактического капа.

   **Ложное доказательство:** стенды проверяют конечность результата и пропорциональность `d_fix`, но ни один не подаёт расходящиеся даты баров. `at_close` доказывает тип цены, не общий момент.

### P1 — остановка управления позицией

6. **`live/autopilot.sh::tick` — смерть после `ST.save`, восстановление после края окна всё ещё выдаётся за пропущенную торговлю.**

   После состоявшейся сессии книга уже несёт сегодняшнюю дату, но `traded-$day` не успел появиться. Если машина вернулась после `trade_till`, выполняется:

   ```bash
   [ ! -e "$ST/traded-$day" ]
   alarm_write ... "тики торгового окна пропущены"
   ```

   `traded_today`, умеющий узнать факт по книге, здесь не вызывается. Автопилот ставит ложный `ALARM-missed` и блокирует следующие сессии и ролл, хотя брокер и книга уже отторгованы.

   Новый стенд повтора проверяет только повтор внутри торгового окна; переход времени через `trade_till` он не проходит.

7. **`live/autopilot.sh::counter_read`, `backup_state` — семейство счётчиков исправлено не полностью.**

   Два независимых отказа:

   - `backup_state` по-прежнему читает `push-fails` напрямую:

     ```bash
     pf=$(cat "$ST/push-fails")
     pf=$((pf + 1))
     ```

     Содержимое `x` под `set -u` убивает shell до тревоги и до `closed-$day`.

   - `counter_read` принимает `08`/`09` как цифровое значение, но Bash разбирает такие литералы как восьмеричные. Следующая арифметика завершается фатальной ошибкой до `alarm_write`.

   Это снова делает пороги отказов шлюза, О-3-Е и выгрузки недостижимыми именно после порчи файлов счётчиков. Утверждение «все счётчики читаются через `counter_read`» фактически неверно.

### P2 — порча и ложное заверение состояния

8. **`live/worm_anchor.py::_attested_paths`, `_tar_state`, `attested_missing_from_archive` — архив может успешно заверить отсутствие обязательных файлов.**

   Замер маржи и журнал МР добавляются только если существуют, конфигурация развёртывания вообще не попадает в ожидаемый список при отсутствии. Проверяющий затем делает:

   ```python
   if not _p.exists():
       continue
   ```

   Поэтому удалённые `margins_live.json`, журнал МР или deploy-конфигурация дают успешный снимок, а не `reject_archive`. Код не отличает «никогда не было» от «утрачено перед резервированием».

   Дополнительно проверяются только имена членов. Если путь реестра/маржи — symlink, `Path.is_file()` проходит, а `tarfile` при стандартном `dereference=False` кладёт ссылку, не байты. После потери машины ссылка битая, но `getnames()` зелёный.

   **Ложное доказательство:** штатный WORM-стенд задаёт путь `margins_live.json`, но сам файл не создаёт. Нет зонда на отсутствие каждого из четырёх членов, на тип tar-члена и на совпадение хэша архивированного содержимого с якорем.

9. **`live/autopilot.sh::backup_state` — ротация архивов всё ещё определяет поколения по изменяемому `mtime`.**

   ```bash
   ls -1t "$bdir"/addfut-*.tgz | tail -n +61 | xargs rm -f
   ```

   `touch`, checkout, восстановление каталога или копирование с сохранённым временем меняют порядок. Старый архив можно сделать «новым», а фактически последнее поколение удалить. Исправление определения последнего WORM-якоря по имени не закрывает соседнюю ротацию самих резервных копий.

   Траекторный стенд с 65 последовательно созданными файлами снова ничего не докажет: в нём `mtime` по построению совпадает с поколением.

10. **`live/contour_test.py` — заявленная безусловная изоляция стенда не выполнена.**

   Используется:

   ```python
   os.environ.setdefault('ADDFUT_LOCK_DIR', tempfile.mkdtemp(...))
   ```

   При унаследованном боевом `ADDFUT_LOCK_DIR` значение не заменяется. Поскольку `state.lock_dir()` отдаёт окружению приоритет даже перед явным `tmp`, сценарии `run_session` и `hold_book_lock(tmp)` берут настоящий `~/.addfut/addfut-book.lock`.

   Стенд способен задержать живую сессию до края окна или конкурировать с роллом. Чистое окружение в `release.py` доказывает только выпускной запуск, но не самостоятельный запуск батареи, для которого комментарий обещает изоляцию.
