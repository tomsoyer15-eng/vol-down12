# Рецензия сорок пятого круга ред. 33 (gpt-5.6-sol, pro+max)

1. **P0 — неверная позиция при маржинальном стрессе. `live/autopilot.sh`, `tick()`**

   Все три вахты О-3-Е смешивают stdout и stderr (`2>&1`), а затем требуют, чтобы весь ответ начинался с `LOW ` или `OK `. Законный ответ шлюза вида

   ```text
   Error 2104 ... farm connection is OK
   LOW 1.200
   ```

   попадает в `*)`: запуска с `session.py --o3e` не будет, только счётчик «слепоты». Через три тика появится тревога, но предписанное сокращение в ту же сессию уже пропущено. Стенды этого не видят: они не подают перед маркером фактические диагностические строки IBKR.

2. **P0 — незаконный COMPLETE при фактическом запасе ниже О-3-Е. `transition.py`, `_execute_locked()` / `pv_remainder()`; `live/ib_broker.py`, `IBBroker.preview()`**

   При полностью исполненном, но ещё не завершённом resume `pv_remainder()` возвращает пустой план. Тогда вызывается `preview()` без `orders`, а он разрешает любую книгу с cushion `>= 1.0`:

   ```python
   if float(_c) < 1.0 and not orders:
       return False
   if not orders:
       return True
   ```

   Книга с живым запасом 1,20 при нормативе 1,40 получает COMPLETE. Финальный `gross()` проверяет модельное плечо, а не живое maintenance requirement, поэтому эту дыру не закрывает. После европейского окна автоматический О-3-Е уже не сможет сократить позицию.

3. **P0 — resume просматривает не остаток фактического перехода. `transition.py`, `pv_remainder()` / `_execute_locked()`**

   Из предпросмотра исключаются только целиком завершённые `st['done']`. Внутрилотовый `st['partial']` и прогресс, который будет восстановлен из позиций брокера, не вычитаются; более того, фактический прогресс разбирается уже **после** preview. Законный частично исполненный переход просматривается как повторная покупка полной цели, получает ложные POSTPONED и на третьем отказе — MIXED.

   Ложное доказательство: сценарий «предпросмотр resume спрашивает остаток» моделирует только целый лот в `done`. Мутации `pv_remainder` в `mutation.py` вообще нет, несмотря на комментарий про «одну точку мутации».

4. **P0 — поставочный сторож fail-open. `live/daily.py`, `run_session()`, `leg_roll_due()`, `leg_roll_overdue()`**

   В `run_session()` любая ошибка календаря отключает проверку пропущенной сессии:

   ```python
   except Exception:
       _prev_s = None
   ```

   В `leg_roll_due/overdue()` любая ошибка тем же способом превращается в «ролл не нужен»:

   ```python
   except Exception:
       return False
   ```

   Связка опасна: после пропущенного дня ролла код может разрешить следующую сессию и оставить либо даже увеличить старую серию. До месяца поставки `delivery_risk()` молчит. Это ещё как минимум два места семейства «ошибка кода переодета в доменный ответ», которое объявлено почти закрытым.

5. **P1 — переход разрывается после первой пары на законном европейском календаре. `live/ib_broker.py`, `_venue_prev()`, `unit_ref()`, `gross()`**

   `_venue_prev()` различает только «фонд/не фонд» и для обоих фондов применяет объединённый календарь LSE/SIX. Но `feed.build_market()` уже признаёт, что после односторонних праздников CSPX и CBU0 имеют разные свежие даты.

   Например, на 05.05.2026 объединённая предыдущая сессия — 30.04, тогда как последние бары фондов — 01.05 и 04.05. Предполет `unit_ref(at_close=False)` проходит по текущей котировке; после первой исполненной пары `gross()` вызывает `closes(expected_prev=30.04)` и падает. Итог — MIXED с уже изменённой позицией.

   Ложное доказательство `_a44cal` проверяет только CME против всей Европы 03.07, но не различие LSE против SIX — именно отсутствующую ветку.

6. **P1 — законная пустая книга Е детерминированно объявляется слепотой. `live/autopilot.sh`, `tick()`**

   При обеих выключенных ногах `margin_cushion()` законно возвращает `None`. Python-сессия умеет отличать пустую книгу от неполной сводки, shell-вахта — нет: `SKIP запаса нет` трижды увеличивает счётчик и создаёт `ALARM-o3e-blind-*`.

   Между 08:45 и закрытием Европы гарантированно есть больше трёх тиков. Поэтому маршрут Е с нулевой позицией сам себя останавливает до следующего ручного разбора. Это незаконно закрытый путь после ужесточения вахты.

7. **P1 — повреждение журнала после первого сбоя записи. `live/journal.py`, `read()`, `verify()`, `append()`**

   `read()` проверяет схему только внутри цикла строк. Нулевой файл или файл с повреждённым заголовком и без данных возвращает `[]`; `verify()` считает его исправным.

   Затем `append()` определяет необходимость заголовка только так:

   ```python
   new = not path.exists()
   ```

   Для существующего пустого файла первая строка пишется без заголовка. На сессии без заявок это может завершиться кодом 0 и сохранённой книгой; на торговой сессии состояние успевает сохраниться до отказа записи ИТОГа. После этого WORM и следующие сессии заперты на повреждённом §7, а брокер и книга уже изменены. Такой нулевой файл достижим смертью сразу после `open(..., 'a')`.

8. **P1 — разные писатели одной книги берут разные замки. `live/state.py`, `lock_dir()`; `live/daily.py`, `run_session()`; `live/session.py`, `do_close()` / `do_o3e_cut()`**

   `run_session()` пытается запирать `bp.parent`, но `do_close()` и `do_o3e_cut()` вызывают `hold_book_lock()` без пути. При законном ручном `ADDFUT_BOOK_PATH` и без `ADDFUT_LOCK_DIR` торговля запирает каталог переопределённой книги, а замыкание и О-3-Е — `~/.addfut`.

   Два процесса могут одновременно читать и сохранять один book-файл под разными flock. WORM также запирает штатный каталог и архивирует его, хотя хэширует внешнюю книгу: возможны потерянная запись и заверенная копия без самих байтов книги. `env_guard` защищает только оболочку автопилота, не документированный прямой вход `session.py`.

9. **P1 — пятый широкий перехват найден. `transition.py`, `_execute_locked()`**

   Вызов недавнего `_preflight_handover()` всё ещё накрыт:

   ```python
   except Exception as _exph:
       raise Incident('предполётная проверка ...')
   ```

   `TypeError`, `AttributeError`, `NameError` и прочие ошибки кода снова становятся доменным «предполет не пройден». Это особенно дорого на аварийном Е→Ф: законный выход блокируется с ложным диагнозом вместо трассировки. Здесь нет исключения через `state.CODE_ERRORS`, хотя в соседних `preview` и `_order_gate` оно уже добавлено.

10. **P2 — ложное WORM-доказательство согласованности реестра и замера. `live/first_connect.py`, `main()`; `live/worm_anchor.py`, `_anchor_body()` / `_attested_paths()`**

    `first_connect` сначала атомарно заменяет реестр, а при любом последующем отказе whatIf оставляет старый `margins_live.json`. WORM лишь независимо хэширует оба файла и проверяет их наличие. Он не сравнивает:

    - `_meta.series`;
    - `_meta.con_ids`;
    - `_meta.account`;
    - поколение реестра.

    Поэтому утверждение из контекста «реестр заменён, замер нет — с обязательностью замера якорь откажет на каждом замыкании» ложно. Якорь успешно заверит несовместимую пару и позволит поставить `closed-*`. Несогласованность обнаружится только позже в `_live_margins()`, возможно уже при срочном переходе. Отрицательного WORM-стенда «оба файла существуют, но поколения расходятся» нет.

11. **P2 — `gross()` всё ещё смешивает два поколения доходности. `live/ib_broker.py`, `IBBroker.gross()` / `unit_ref()`**

    Для ZN один вызов `gross()` дважды запрашивает TNX:

    1. `unit_ref(..., at_close=True)` строит полосу по первому `yield_pct`;
    2. ветка ZN в `gross()` заново вызывает `yield_pct` и считает единицу по второму.

    Комментарий «одно чтение доходности на весь расчёт» коду не соответствует. Исправление/перепубликация бара между запросами даёт полосу поколения A и плечо поколения B; широкая полоса D=3..12 это обычно пропустит. Ворота 2,00 могут завершить переход по величине, которой не существовало в одном снимке. Стенд использует статичные бары и этого не различает.

12. **P2 — диагност снова выдаёт взаимоисключающие причины. `live/diagnose.py`, `SIGNS`, `main()`**

    Реальные тревоги `_alarm_o3e()` одновременно содержат `О-3-Е` и фразу «по нормативу §8». Поэтому `main()` печатает:

    1. верную причину про маржинальный запас;
    2. ложную причину «капитал ниже порога §8 маршрута».

    Комментарий «якоря пересечься не могут» неверен. `_a44dg` извлекает только `Вероятная причина 1`, поэтому лишний противоположный диагноз не наблюдает.

13. **Ложное покрытие шести методов. `live/ib_broker.py`, `SAME_API()`; `live/mutation.py`, `run_adapter_mutations()`**

    Классификация оставшихся методов:

    - `buy_units`, `sell_units` — денежная граница, обязательны мутации. Инверсия действия удвоит источник или продаст цель. Текущий SAME_API сверяет только модуль возвращённого fill и не проверяет изменение позиции/направление заявки.
    - `mark_pair`, `minutes_since` — денежная защита длительности непарной позиции, не ритуал.
    - `todays_executions` — денежная защита ABORT против MIXED и повторной подачи, не ритуал.
    - `_px_hint` — вспомогательный: влияет прежде всего на §7; `place()` всё равно заново снимает котировку и самостоятельно подаёт заявку. Его отдельная мутация для позиции была бы в основном ритуалом.

    При этом заявление «у всех шести нет мутаций» уже не соответствует файлу: `pair_clock_wall` мутирует `mark_pair`. У остальных прямой мутационный контроль действительно отсутствует. Особенно опасно, что `run_adapter_mutations()` судит только `run_adapter()`, а не `SAME_API()`: сам факт вызова обёрток в другой сетке их мутации не ловит.
