## P0 — дефекты, способные прямо привести к убытку

### 1. Боевого контура маршрута Е не существует

**Место:** `r33build/live/daily.py`, функции `units()`, `step()`, `book_to_orders()`.

Параметр `route='E'` влияет только на проверку порога в `guards()`. После этого код всё равно:

- считает единицы ES/MES и ZN;
- хранит `n_e`, `n_b`, `d_fix`;
- формирует заявки только в ES/MES/ZN.

CSPX, CBU0, дебет, 5%-ный кэш и О-3-Е там отсутствуют. `sim_etf.py` — бэктест, а не live-контур. Следовательно, после `transition.py`, который способен записать переход в Е, ежедневного исполнителя для нового маршрута нет. Если вызвать `daily.step(..., route='E')`, он не просто «не умеет Е», а продолжит рассчитывать фьючерсную книгу.

Это напрямую противоречит `ADD-FUT-v1_6_0-r33.txt`, §8 и §12, где бумажный этап должен вести две книги Е и проверять ежедневный контур.

### 2. Физический ролл сломан: на следующий день система откатывается в старый контракт

**Место:** `r33build/live/daily.py`, `series_code()`, `rolled_series()`, блок серий в `step()`.

Конкретный путь:

1. 26.08.2026, `roll_today=True`: `ZNU26 → ZNZ26`.
2. 27.08.2026, `roll_today=False`: `series_code('ZN', 27.08)` снова возвращает `ZNU26`.
3. `step()` видит, что удерживается `ZNZ26`, и формирует обратный перенос `ZNZ26 → ZNU26`.
4. 01.09.2026 код снова перейдёт в `ZNZ26`.

То есть получаются три ролла вместо одного, включая повторный вход в контракт после нормативной даты ролла и вблизи зоны поставки. После пропуска сессии ролла или перезапуска проблема ещё хуже: код не знает, что дата ролла уже прошла, поскольку хранит только серию, а не факт пройденного ролла.

`live/contour_test.py` проверяет только сам день 26.08 и не проверяет 27.08, конец августа, 01.09 или восстановление после пропущенного ролла.

### 3. Даже исправленный ролл может вообще не быть отправлен брокеру

**Место:** `r33build/live/daily.py`, свойство `Decision.trade`.

```python
@property
def trade(self):
    return bool(self.orders) and not self.refusals
```

При чистом ролле число контрактов не меняется, поэтому `orders` пуст, хотя `roll_pairs` содержит закрытие старой и открытие новой серии. `dec.trade` в таком случае равен `False`.

Любой естественный вызывающий код вида `if dec.trade: place(book_to_orders(...))` пропустит ролл. Тест специально проверяет, что ролловые заявки возникают при неизменном количестве, но не проверяет `rd.trade`.

### 4. «Полный отказ» замораживает опасную позицию вместо её сокращения

**Место:** `r33build/live/daily.py`, конец `step()`:

```python
if d.refusals:
    d.orders = {}
    d.roll_pairs = []
    d.book_after = book
```

Если NLV действующего маршрута Ф упал ниже 3 млн либо половина шага перестала помещаться в полосу, код отменяет вообще все заявки, включая:

- закрытие ноги по сигналу;
- кап-коррекцию;
- уменьшение плеча;
- выход из старой поставочной серии.

Таким образом, падение счёта в кризис способно одновременно включить запрет Ф и заблокировать спасительное сокращение. Это особенно опасно после хвоста −58,5%: счёт, стартовавший около порога, неизбежно окажется сильно ниже него.

В `live/contour_test.py` проверяется отказ только на фактически пустой книге. Нет теста «существующая позиция + NLV ниже порога + сигнал закрытия/ролл/кап».

### 5. Жёсткий порог 3 млн обходится переходным исполнителем

**Место:** `r33build/transition.py`, `execute()` и `preflight_margin_orders()`.

В `transition.py` вообще нет проверки `MIN_NLV_F`. Более того, `selfcheck_v192.py`, тест:

> `Исполнитель: round-trip автоматичен`

явно выполняет переход `E → F` при капитале **1 млн** и считает `COMPLETE` успехом. То есть тест канонизирует прямое нарушение §8, где Ф недоступен ниже 3 млн независимо от разрешений гранулярности.

Практический путь нарушения не требует ручной подделки журнала: сигнал в Ф мог появиться при NLV выше 3 млн, затем капитал упал до исполнения. `OWNER_APPROVE` остаётся действительным, а исполнитель текущий порог не перепроверяет.

Дополнительно `capital` передаётся вызывающим кодом и не сверяется с `broker.net_liquidation()`. После такого перехода `daily.py` начнёт блокировать все заявки по пункту 4.

### 6. «Контурные тесты» не тестируют реакцию контура на сбои

**Место:** `r33build/live/contour_test.py`, разделы 3 и 3а.

Для `partial`, `overfill`, `reject`, `disconnect` тест просто вызывает:

```python
b.place('ZN', 101)
```

и проверяет, что фиктивный брокер вернул ожидаемое слово. Ни `daily.step()`, ни состояние книги, ни журнал, ни восстановление после частичного исполнения здесь не участвуют.

Ещё показательнее тест ролла:

> `ролл: отказ на открытии новой серии виден как разрыв`

Он объявляет PASS, когда старая серия уже закрыта, новая не открыта и книга осталась без требуемой экспозиции. Обнаружить разрыв — не значит безопасно его обработать. Кода, который повторяет открытие, откатывает закрытие, ставит состояние MIXED и блокирует следующую сессию, нет.

### 7. Ежедневный контур не согласован с МР и переходным исполнителем

**Место:** `r33build/live/daily.py` целиком.

`daily.py`:

- не читает маршрут из `mr_journal.csv`;
- не проверяет `pending`/`MIXED`;
- не захватывает `mr_engine.hold_strategy_lock`;
- не сверяет фактическую книгу брокера;
- не имеет атомарного состояния или идемпотентного session-id.

Следовательно, ежедневный ребалансировщик Ф может работать одновременно с `transition.py`, продающим ту же книгу для перехода в Е. Это реальная гонка с двойными или встречными заявками. Утверждение §8 о восстановлении после перезапуска также не подтверждено: `Book` — только dataclass, кода сохранения и восстановления ежедневного состояния нет.

### 8. Execution-mapper занижает оборот и издержки до 19 раз

**Место:** `r33build/sim_v164.py`, `map_mes()`; `r33build/live/daily.py`, `book_to_orders()`.

Контрпример:

- было `n_e=9` → книга `0 ES + 9 MES`;
- стало `n_e=10` → каноническая книга `1 ES + 0 MES`.

Симулятор считает изменение всего на **1 MES** и списывает издержки с одного шага. Физическое отображение выдаёт:

- купить `1 ES`;
- продать `9 MES`.

Это gross-оборот в 19 MES-эквивалентов ради изменения экспозиции на один MES. При шаге $38 428 модельная база издержек — $38 тыс., физическая — около $730 тыс.

Самопроверка доказывает только тождество `10*ES + MES = n`. Она не проверяет путь между двумя книгами, оборот или фактическую комиссию. Поэтому показатели сессий и издержек, использованные для оправдания полосы 10%, не соответствуют собственному execution-mapper.

### 9. О-3 и О-3-Е не реализованы в ежедневной торговле

### 10. В переходном исполнителе есть несколько путей к незахеджированной книге

**Место:** `r33build/transition.py`.

1. **Неподтверждённая отмена при аварии.** В `fail()` результат `cancel_order()` игнорируется:

   ```python
   for oid in broker.open_orders():
       broker.cancel_order(oid)
   ```

   В `resume` строго требуется `is True`, а в аварийном пути — нет. Ордер может исполниться после записи ABORT/MIXED.

2. **Нулевая заявка после уже совершённой продажи.** В `_run_lots()`:

   ```python
   want = max(0, int(round(...)))
   broker.buy_units(lot['dst'], want)
   ```

   Проверки `want > 0` нет. При переходе CBU0→ZN остаток менее половины одного ZN сначала продаётся, после чего отправляется покупка нулевого количества. `FakeBroker` такую заявку отвергает, оставляя MIXED.

3. **Лимит 390 заявок считается неверно.** `plan_orders()` предполагает максимум три заявки на лот, но `_run_lots()` содержит цикл по частичным исполнениям и дополнительные компенсационные заявки. При серии partial fills число заявок не ограничено этим расчётом.

### 11. `OWNER_APPROVE` не является аутентифицированным одобрением владельца

**Место:** `r33build/mr_engine.py`, `approve_switch()`, `find_approval()`, `journal_rows()`.

Одобрение — обычная строка CSV:

```text
OWNER_APPROVE,E|sid
```

Нет подписи владельца, отдельного ключа, ACL-проверки или привязки к сумме/плану/`tid`. CLI `--approve-switch` может запустить любой процесс с доступом к файлу.

Вся сложная защита `st_dev/st_ino` обнаруживает замену файла, но не изменение содержимого на месте. Не кооперирующийся писатель может дописать или переписать строки в том же inode, проигнорировав advisory `flock`. В отличие от журнала издержек, MR-журнал даже не имеет цепочки хэшей.

Одобрение также привязано только к `sid` и направлению. После него исполнитель может получить другой капитал, цены и план, не запрашивая нового акта владельца.

## P1 — метод и риск-выводы, на которые нельзя опирать деньги

### 12. Проверка полосы 10% выполнена не на нормативной механике

**Место:** `tools/band_recheck.py`, `sim_stats()` и `match()`; `ADD...`, §2.

В `sim_stats()` нет нормативного кап-блока:

- не хранится `prev_close_lev`;
- нет коррекции следующей сессией;
- нет одностороннего целочисленного аллокатора;
- вместо этого лишь масштабируется цель, если её сумма выше `cap*e`.

Ролловая стоимость списывается только с ноги Б:

```python
if roll:
    e -= S.ROLL_BP * ex[1]
```

тогда как `sim_v164.py` списывает её с обеих ног. Поэтому приведённые в §2 фазовые и risk-matched числа не являются результатом боевого движка.

Дополнительно `match()` подбирает множитель по реализованной волатильности на той же истории и одновременно меняет cap. Это не независимое сравнение риска, а новая подгонка на выборке.

---

### 13. Основание «недоэкспозиции нет» не следует из измерений

**Место:** `ADD...`, §2; `tools/band_recheck.py`.

Текст утверждает:

- отклонение симметрично;
- позиция одинаково часто выше и ниже цели;
- недоэкспозиция объясняет не более пятой части разницы CAGR.

Но `sim_stats()` не считает ни число отклонений вверх/вниз, ни P&L-атрибуцию. Там есть только средняя экспозиция и абсолютный отрыв.

Даже симметричная частота ничего не доказывает: экономический эффект определяется ковариацией ошибки экспозиции с последующей доходностью. Недовес на росте и перевес на падении может давать систематический ущерб при одинаковом количестве знаков. Число «не более пятой части» в представленном коде не выводится.

### 14. Выбор 10% остаётся подгонкой после просмотра результата

**Место:** `tools/band_recheck.py`, `BANDS`; `ADD...`, §2.

Фактически проверены четыре точки:

```python
BANDS = [0.03, 0.05, 0.10, 0.15]
```

После просмотра CAGR, просадки, числа сессий и кап-коррекций заказчик выбрал 10%. Нет:

- заранее объявленной функции потерь;
- holdout-периода;
- walk-forward;
- проверки соседних значений;
- штрафа за максимальную разовую сделку и кризисную ликвидность.

Аргумент «решение заказчика» не превращает ретроспективный выбор в априорный. Главная выгода — экономия оборота, но цена оборота как раз остаётся непроверенной (§7).

### 15. «Точная механика Депрессии» работает на искусственно сглаженной ноге Б

**Место:** `r33build/depr_real.py`, `build()`; `ADD...`, §4 и §9в.

Месячная доходность облигаций равномерно размазывается по всем дневным наблюдениям:

```python
bd_d[...] = (1 + val) ** (1 / n) - 1
```

Это по построению уничтожает:

- внутримесячную волатильность;
- гэпы;
- дневную корреляцию с акциями;
- реальные кап-срабатывания;
- маржинальные пики.

Сам документ в §9в признаёт, что нога Б до 1962 года «для суждения о её дневной качке непригодна», но §2 и §4 используют её именно для дневной полосы, фаз, максимального плеча и кап-коррекций.

Поэтому 2,1201 и 9,7% — не стрессовые верхние оценки, а результаты на сглаженной траектории.

### 16. Старая и новая Депрессия сравниваются на разных моделях доходности облигаций

**Место:** `r33build/depr_v13.py` против `r33build/depr_real.py`.

В старой модели есть выпуклость:

```python
+ 0.5 * Cv.shift(1) * dyy**2
```

В новой она полностью удалена:

```python
bdm = y10.shift(1) / 12 - Dv.shift(1) * dyy
```

Следовательно, разница −7,7% → −6,0% включает не только полосу, целые контракты и кап, но и изменение экономической модели ноги Б. Вывод «прежняя оценка была консервативна» из такого сравнения не следует.

Чувствительность гранулярности тоже односторонняя: проверена сетка в 10 раз мельче, но не в 10 раз крупнее.

### 17. «Предельное плечо конструкции 2,15×» нигде не ограничивается кодом

**Место:** `ADD...`, §5; `sim_v164.py`; `live/daily.py`.

В коде есть cap 2,00, проверяемый следующей сессией. Значения 2,15 как аварийного ограничения нет вообще. `close_out()` лишь сохраняет фактическое плечо; он не закрывает позиции.

При достаточно большом однодневном совместном падении ног плечо может стать 2,3×, 3× или выше. Исторический максимум 2,1201 — наблюдение на одной синтетической траектории, а не конструктивная граница. Формулировка «предельное плечо конструкции» ложна.

То же относится к внутридневному плечу: все заявленные максимумы рассчитаны по закрытиям.

### 18. Мандат просадки переписан под уже увиденный провал

**Место:** `ADD...`, §5.

Хвост поднят до −58,5% ровно после обнаружения −58,4%. Это не устранение риска, а устранение нарушения путём передвижения лимита. Запас 0,1 п.п. меньше неопределённости издержек, данных, исполнения и валюты.

В том же разделе остаётся внутреннее нарушение:

- штатный бюджет: −35%;
- худшая фаза ядра: −35,8%.

То есть стратегия уже не проходит заявленный штатный бюджет, но он не изменён и действие при нарушении не определено.

Оценка частоты «один раз за 63 года, два эпизода за 141 год» не является статистической моделью хвоста: два события не позволяют оценить вероятность или верхнюю границу тяжести.

### 19. Журнал издержек систематически неправильно измеряет ролл

**Место:** `r33build/live/journal.py`, `_cost_bp()` и `reconcile()`; `sim_v164.py`.

Симулятор списывает ролл один раз:

```python
ROLL_BP * position_notional
```

Физический журнал содержит две сделки — закрытие старой и открытие новой серии. `_cost_bp()` включает в знаменатель обе, то есть примерно `2 × notional`. Одинаковая долларовая потеря 1 б.п. от позиции будет показана как примерно 0,5 б.п. Это механическое занижение цены ролла вдвое.

Кроме того:

- `roll_spread_near` и `roll_spread_far` вообще не используются в расчёте;
- все строки с `reason/note`, содержащими «ролл», смешиваются в один блок, включая сопутствующее изменение количества;
- время и источник benchmark-цены не фиксируются.

Такой журнал не способен проверить норматив 1 б.п.

### 20. Порог двадцати наблюдений для роллов фактически не действует

**Место:** `r33build/live/journal.py`, `reconcile()`.

Сначала проверяются 20 различных дат по всем сделкам вместе. Затем блок роллов рассчитывается даже по одной строке:

```python
if len(sessions) < MIN_OBS: ...
...
roll = block([...], ...)
```

У блока `roll` нет собственного требования 20 ролловых сессий. В `contour_test.py` после 25 обычных сессий и всего четырёх роллов код уже выдаёт ролловый вердикт и считает это PASS.

Также в журнале нет поля для доли объёма ZN. Поэтому обещанный в §7 триггер «ниже 40%» технически невозможно рассчитать.

### 21. Известная ошибка сайзинга ZN оставлена в нормативе

**Место:** `ADD...`, §3; `sim_v13.py`, `CTD_RATIO=0.88`.

Документ сам установил:

- согласующий коэффициент `c*=0,786`;
- при `0,88` фактическая экспозиция ноги Б равна 89,4% цели.

Это означает примерно 101 контракт вместо порядка 113 для заявленной длительности. При этом документ продолжает называть ногу целевой `1,0 × капитал`.

Аргумент «CAGR 14,03 против 14,01» — совпадение агрегата за выбранные 44 года. Он не проверяет:

- режимные подпериоды;
- просадку;
- cap events;
- кризисную корреляцию;
- роль облигаций как хеджа;
- фактическую книгу с целыми контрактами.

Известную 11%-ную ошибку нельзя оставлять «открытым пунктом», одновременно объявляя Ф маршрутом по умолчанию.

---

### 22. Выводы о маржинальной безопасности не поддержаны данными

**Место:** `live/margin_check.py`; `ADD...`, §3 и §8а.

Исторических SPAN/house requirements нет. Требование получено умножением текущей ставки на произвольное отношение реализованных волатильностей. Это не модель SPAN: отсутствуют сканирующие сценарии, корреляционные offsets, concentration add-ons, ликвидность и внутридневные изменения house margin.

Для Е «историческая» проверка вообще сводится к тождеству:

```python
cushion = 1 / (fixed_pct * leverage)
```

То есть минимум 1,95× при 25% не является независимым результатом — это просто максимум плеча 2,0518, подставленный в фиксированные 25%.

Есть и кодовая ошибка датировки: `sim_etf.py` добавляет в `record` только дни с `lc > 0`, а `margin_check.route_e()` при несовпадении длины приписывает эти значения последним датам окна. Минимальное значение сохраняется, но объявленная дата минимума может быть неверной.

---

### 23. Пилот по-прежнему не проверяет основной денежный риск маршрута Ф

**Место:** `ADD...`, §8.

Этап 1 Ф на 10 млн — бумажный, то есть не проверяет fills, bid/ask, impact и аварии брокера. Этап 2 — живые 10%, то есть около 1 млн, где Ф запрещён порогом 3 млн. Следовательно, Ф может перейти из бумажной симуляции сразу в полную живую книгу 10 млн без живого пилота.

Дополнительные пробелы:

- у этапа 2 нет критерия завершения;
- 20 live-сессий при 7,3–17 сессиях в год потребуют примерно 1,2–2,7 года;
- `daily.step()` использует полный broker NLV и не умеет вести 10%-ную виртуальную аллокацию внутри счёта;
- не сказано, должен ли пилот быть отдельным счётом на 1 млн.

---

### 24. Результаты маршрута Е основаны не на торгуемых инструментах

**Место:** `r33build/sim_etf.py`, заголовок и `sim_etf()`.

Код прямо признаёт PRE-LAUNCH PROXY:

- CSPX заменён SPY;
- CBU0 заменён индексом на IEF;
- период до запуска фондов моделируется.

При этом игнорируются расхождения времени закрытия LSE и США, реальные спреды, holiday mismatch, tracking difference и фактические правила займа. Прокси-цена CBU0 в симуляции начинается со 100, тогда как `transition.py` и тесты используют около $5; значит целочисленность, число заявок и оборот моделируются на другой сетке.

На этой базе порог маршрутизации публикуется с точностью до сотых п.п., что не соответствует точности входов.

---

### 25. Решение не сдвигать ролл основано на данных, которые не измеряют спорный эффект

**Место:** `ADD...`, §9г.

Плоский календарный спред по settlement prices измеряет carry между датами, но не bid/ask, depth и market impact. Именно эти величины являются причиной сдвигать ролл при падении доли объёма с 66–68% до 43,3%.

Формулировка «измеримая часть эффекта равна нулю» подменяется выводом «менять не следует». Корректный вывод: главная часть эффекта не измерена. Более того, обещанный live-триггер 40% не может работать из-за отсутствия соответствующего поля в `journal.py`.

---

### 26. Реестр отклонённых защит построен на зависимых проверках и круговой логике

**Место:** `ADD...`, §9а.

Окна 1963–2026 и 1886–2026 не являются независимыми: первое полностью вложено во второе. 360 сценариев, «взвешенных по исторической частоте», также построены на той же истории; генератор, параметры и данные в пакете отсутствуют.

Стоп по просадке — единственный кандидат, улучшивший хвост во всех заявленных проверках. Он отклонён в том числе потому, что «противоречит решению “стопов нет”». Это круговая аргументация: кандидат отвергается потому, что исходная спецификация уже решила его не использовать.

У путов котировок нет, но делается односторонний вывод, что реальная цена обязательно выше модельной. Это не доказано без фактической поверхности IV, skew, правил ролла и ликвидности.

---

### 27. Решение сохранить смещённый сигнал зависит от текущего режима и потому тоже ретроспективно

**Место:** `ADD...`, §9б.

Исправленный сигнал по избыточной доходности улучшает полное окно, но отвергается потому, что текущая ставка находится в диапазоне 3–6%, где он исторически проигрывал. Это режимный выбор после разбиения истории и с оглядкой на текущий уровень ставки, а не априорное правило.

Порог возврата «устойчиво выше 6%» выбран из тех же наблюдавшихся корзин. Нет определения «устойчиво», нет задержки/гистерезиса и нет теста пути быстрого роста ставки через 6%.

### 33. Ключевые исследования, которыми обоснованы решения, не воспроизводятся из пакета

**Место:** `tools/band_recheck.py`; `MANIFEST-192.txt`; `MANIFEST.txt`.

### 34. «Совпадение книг» не охватывает физическую книгу

**Место:** `r33build/live/replay_check.py`.

Сравниваются только массивы:

```python
(n_e, n_b)
```

Не сравниваются:

- серии контрактов;
- отображение ES/MES;
- gross-оборот отображения;
- `roll_pairs`;
- фактические заявки;
- fills;
- отказы guards.

Более того, replay запускает `check_guards=False`. Поэтому он не мог обнаружить ни откат Z→U после ролла, ни `Decision.trade=False`, ни 19-кратный оборот map_mes, ни замораживание книги ниже 3 млн. Формулировка «КНИГИ совпали на каждой сессии» существенно шире реально выполненной проверки.

### 35. Таблица изъятий в §5 не поддержана включённым кодом

**Место:** `ADD...`, §5; `r33build/code/withdraw.py`.

`withdraw.py` моделирует только фильтр на одной ноге акций:

```python
px = mk['Adjusted Close']
```

Там нет второй ноги, плеча 2×, полосы, капа, контрактов и механики редакции 33. Скрипт считает 30-летние скользящие окна и инфляционно индексированные изъятия от стартового капитала, тогда как §5 публикует другой опыт — вход в сентябре 1929 года и изъятия от пика.

Дополнительно сам текст говорит для 2%:

- «6,8 года под водой»;
- затем «готовность шестнадцать лет не видеть прежнего уровня».

Без определения разных метрик эти утверждения противоречат друг другу.

### 36. Скрипт запуска шлюза оставляет файл с паролем

**Место:** `r33build/live/ibgw/start.sh`.

Создаётся временный `config.ini` с открытым `IbPassword`, а очистка назначена через `trap`. Последняя команда:

```bash
exec "$IBC_DIR/gatewaystart.sh" ...
```

успешно заменяет shell-процесс, поэтому EXIT-trap оболочки после нормального завершения уже не выполняется. Временный файл с учётными данными может остаться на диске, как и Xvfb. Для финансового шлюза это не мелкая эксплуатационная проблема.
