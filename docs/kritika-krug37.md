# Рецензия тридцать седьмого круга ред. 33 (gpt-5.6-sol, pro+max)

1. **[P0 — неверная позиция] `live/session.py::_alarm_o3e`, `live/daily.py::run_session`**  
   Тревога ложно утверждает: «Сокращение выполнено автоматикой». Колбэк вызывается **до** вычисления и подачи `_cut_orders`:
   ```python
   if _live_book and (_pc is None or float(_pc) < O3E_MIN):
       o3e_alarm_fn(...)
   ```
   При `_pc is None` срез вообще не выполняется. При низком `_pc` питание может пропасть после fsync тревоги, но до первой заявки среза. В обоих случаях у брокера остаётся книга около 2×, а долговечный файл сообщает оператору, что она сокращена. Стенд «неизвестный запас» проверяет лишь наличие ALARM, не его правдивость.

2. **[P0 — рассинхронизация при переходе] `live/ib_broker.py::IBBroker.gross`, `unit_ref`**  
   `gross()` передаёт в `unit_ref()` класс из живого реестра — `STK`. `unit_ref()` распознаёт фонд только при точном `cls == 'ETF'`. Для CSPX/CBU0 возвращается `None`, после чего `gross()` падает:
   ```python
   if str(cls) == 'ETF': ...
   ...
   raise BrokerError(f'{_inst}: долларовая единица неизвестна')
   ```
   `_run_lots()` вызывает `gross()` после каждой пары. Поэтому живой Ф→Е после первой уже исполненной продажи/покупки уйдёт в MIXED; штатный COMPLETE технически недостижим.

3. **[P0 — неверное плечо] `live/ib_broker.py::IBBroker.gross`, `unit_ref`**  
   Заявленный «gross ФАКТИЧЕСКОЙ книги по котировкам момента» считается по середине проверочной полосы предыдущего закрытия. Для ZN полоса построена по всему диапазону `D=3..12`, а середина не имеет отношения к `book.d_fix`. Например, при `d_fix=12`, `dref=8` фактическая модельная единица около \$147,840, тогда как середина текущей полосы около \$100,700. Плечо может быть занижено примерно на треть и пройти `CLOSE_CAP=2.00` при фактическом превышении. Для ETF/ES также используется вчерашнее закрытие, а не котировка момента.

4. **[P0 — незакрытый хвост маршрута Е] `live/ib_broker.py::IBBroker.sell_units`, `buy_units`**  
   Переходный интерфейс снова уничтожает дробные доли:
   ```python
   -abs(int(units))
   abs(int(units))
   ```
   При выходе из позиции `CBU0 = 2_000_000.5` почти весь переход исполнится, а последний лот `0.5` превратится в нулевую заявку и даст MIXED. Исправление дробей в основном `place()` эту новую обёртку не покрывает.

5. **[P0 — проверка счёта не непосредственно перед заявкой] `transition.py::_execute_locked`**  
   Последняя сверка перед первой заявкой проверяет только количества инструментов-источников:
   ```python
   for ... in spec['src']:
       if position != planned: fail(...)
   ```
   Она не повторяет проверку:
   - появившейся позиции класса цели;
   - постороннего инструмента;
   - полного соответствия счёта книге;
   - свежего NLV, от которого рассчитан лимит 1%.

   Поздняя покупка CSPX или посторонняя позиция между предполётом и этой точкой проходит. Исполнитель затем покупает полную цель поверх неё; расхождение обнаруживается только после собственных заявок.

6. **[P0 — лимит 15 минут не работает] `live/ib_broker.py::IBBroker.minutes_since`, `transition.py::_run_lots`**  
   Первый вызов `minutes_since(key)` происходит только **после** продажи, покупки, компенсации и `gross()`. В этот момент метод создаёт `t0` и возвращает почти ноль:
   ```python
   t0 = _m.setdefault(key, time.time())
   ```
   Одноитерационная пара может исполняться сколько угодно дольше 15 минут и никогда не нарушить тайм-аут. В многоитерационной паре теряется длительность первой итерации.

7. **[P0 — ложный margin preview] `live/ib_broker.py::IBBroker.preview`**  
   Комментарий обещает `whatIf`, но метод не вызывает `whatIfOrder` и вообще не знает план перехода. Он лишь проверяет текущий:
   ```python
   margin_cushion() >= 1.0
   ```
   Здоровый запас исходной книги не подтверждает возможность открыть целевую. При внутридневном повышении house-margin устаревший файловый preflight может пропустить цель, а этот «preview» даст ложное разрешение.

8. **[P0 — «чистый» отказ окна сам подаёт заявки] `live/daily.py::execute_roll`, `bail`, `restore_to`**  
   `WindowClosed` до самой первой заявки вызывает `bail()`, а тот безусловно запускает `restore_to()`. Если между предыдущей сверкой и воротами пришёл поздний fill или ручная сделка, «заявка НЕ подавалась» превращается в автоматические компенсационные заявки, причём `restore_to()` намеренно обходит окно. Чистый отказ может начать торговлю GTC за краем окна и автоматически «лечить» чужое расхождение вопреки О-5.

9. **[P1 — порча замыкания] `live/session.py::do_close`**  
   Замыкатель не проверяет `ST.load_intent(bp)`. После аварии среза О-3-Е на диске может лежать промежуточная сегодняшняя книга и незавершённое намерение с неизвестным исходом. Снимок позиций может временно совпасть, после чего `do_close()`:
   - фиксирует плечо;
   - снимает backup/WORM;
   - позволяет поставить `closed-*`.

   Поздний fill затем меняет брокера уже после заверения ложной книги. Основная сессия разбирает intent до сверки; замыкание эту защиту обходит.

10. **[P1 — Decision после среза всё ещё ложный] `live/daily.py::run_session`**  
    Исправление `daily_costs` сделано умножением всех величин на долю оставшегося номинала:
    ```python
    _dc[k] *= P_after / P_before
    ```
    Это неверно:
    - `debit = max(0, P + 0.05E - E)` не пропорционален `P`;
    - `loan_spread_amt` ступенчатый;
    - `drag` зависит только от ноги А.

    При переходе примерно 2×→1× масштабирование даёт debit около `0.525E`, тогда как фактическая формула даёт около `0.05E`. Кроме того, если повторный замер после среза вернул `None`, `dec.cushion` вообще не меняется и остаётся старым досрезным числом вместо «неизвестно».

11. **[P1 — поставка/мёртвый автопилот] `live/autopilot.sh`, сторож занятого замка**  
    Ветка устаревшего lock выполняется **до определения** функций `alarm_write()` и `log()`. Bash не регистрирует последующие определения задним числом. При lock старше часа выполняются несуществующие команды:
    ```bash
    alarm_write: command not found
    log: command not found
    ```
    Поэтому заявленная многоступенчатая запись ALARM там не работает. Остаётся случайная попытка создать STOP и stderr cron; при ACL/ENOSPC контур снова может выглядеть успешно остановившимся без видимой тревоги и пропустить ролл.

12. **[P1 — STOP этого же тика обходится] `live/autopilot.sh::tick`**  
    После `run_trade` повторно проверяется только `ALARM-*.txt`, но не `autopilot.STOP`. Если запись ALARM не удалась и `alarm_write` поставил STOP, тот же процесс продолжает вахту О-3-Е и замыкание. Исправление «тревога этого тика останавливает тик» применено только к одному из двух межпроцессных барьеров.

13. **[P1 — журнал МР остаётся OPEN без барьера] `transition.py::_execute_locked`, `mr_engine.py::confirm_transition`**  
    `confirm_transition(kind='open')` сначала долговечно дописывает `TRANSITION_OPEN`, затем пишет производный `mr_state`. Если запись кэша падает, наружу выходит исключение уже **после OPEN**. Обработчик `_execute_locked` считает это чистым отказом, снимает обе `handover-inflight-*` и не пишет ALARM/ABORT. В результате журнал держит OPEN, а единственный файловый барьер ежедневного контура удалён.

14. **[P1 — долговечность тревоги перехода неполна] `transition.py::_alarm_transition`**  
    Основное имя fsync-ит каталог, запасное — только файл. При успешном fallback функция возвращает `''`, хотя directory entry не заверена и может исчезнуть после потери питания. В ветке полного отказа STOP пишется через `write_text()` без fsync и без проверки, а ошибка глотается. Утверждение «запасное имя и STOP долговечны» кодом не выполнено.

15. **[P1 — успешный путь перехода недостижим на приложенном состоянии] `live/margins_live.json`, `transition.py::_live_margins`**  
    Файл содержит только U26, не содержит ESZ26/MESZ26/ZNZ26 и вообще не несёт `_meta.con_ids`. Живой реестр содержит обе серии. `_live_margins()` гарантированно откажет сначала по неполному покрытию, затем — по отсутствию поколения. Переходные стенды используют другую временную полную фикстуру, поэтому зелёный выпуск не исполняет конфигурацию снимка.

16. **[P2 — ложное SAME_API] `live/ib_broker.py::SAME_API`**  
    Для перехода проверяются только наличие метода и число параметров. Ни `preview`, ни дробный `sell_units`, ни `minutes_since`, ни `gross` не вызываются. `FakeBroker` переходный интерфейс вообще не реализует. Поэтому SAME_API не способен увидеть дефекты №2–7. Отдельный стенд `unit_ref` передаёт искусственный класс `'ETF'`, скрывая реальный конфликт со `STK`.

17. **[P2 — круговое доказательство ролла] `live/invariants.py::_i17`**  
    Ожидаемая необходимость ролла вычисляется тем же `DL.leg_roll_due`, который управляет production-кодом. Мутация `leg_roll_due = lambda ...: True` заставит и код, и инвариант требовать лишний ролл — тест останется зелёным. Точечных случаев «в день календарного ролла А уже свежая, Б ещё просрочена» нет; последовательности `_rl5/_rl7` проверяют overdue/pending в другие даты.

18. **[P2 — три заявленные парные мутации не наблюдают границы] `live/mutation.py`, `live/invariants.py`**  
    - `pair_margin_off`: нет сценария с часами между `deadline-15min` и `deadline`; случаи Е идут в 09:00 при крае 09:45, а «окно ушло» проверяет жёсткий край. Снятие резерва ничего не меняет.  
    - `attempt_trace_off`: `TR_CASES` не содержит lost-ack, где брокер исполнил первую заявку и упал до возврата номера. Прямые вызовы `_run_lots` не читают `attempted`; поле нигде не утверждается.  
    - `decision_stale_after_cut`: мутируется только `exposure`, хотя объявлены также orders, leverage, capital, daily_costs и cushion. `_r36` проверяет exposure тождеством:
      ```python
      px = exposure / ne
      exposure == ne * px
      ```
      Оно истинно для любого ненулевого stale-exposure. Защита остальных полей отсутствует.
