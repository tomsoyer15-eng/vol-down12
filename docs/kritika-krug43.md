# Рецензия сорок третьего круга ред. 33 (gpt-5.6-sol, pro+max)

### P0 — неверная позиция / пропущенный кап

1. **`live/daily.py::run_session`, обработчик `except RollGap` — откаченный ролл сохраняется как уже замкнутая сессия.**  
   `replace(book, roll_pending=..., last_session=...)` наследует от вчерашней книги `close_provisional=False` и вчерашний `prev_close_lev`. Затем `autopilot.sh::run_close` получает «уже замкнута», проверяет именно `close_provisional is False`, ставит `closed-$day` и снимает WORM-копию. Фактические цены и NLV сегодняшнего закрытия не читаются вообще; следующий день применяет кап по вчерашнему плечу. На провале ролла это ещё и ложное заверение поставочно опасной книги.  
   **Ложное доказательство:** стенды проверяют `execute_roll` либо перенос `last_session`, но не производственную связку `RollGap → ST.save → run_close` и не утверждают `close_provisional=True`.

2. **`live/autopilot.sh::tick` — исправление `traded_today` не дошло до вахты О-3-Е.**  
   Ветка пропущенного окна уже спрашивает книгу через `traded_today "$day"`, но вахта ниже по-прежнему требует физический файл:
   ```bash
   [ -e "$ST/traded-$day" ]
   ```
   После смерти между `ST.save` и `touch traded-*`, если машина вернулась уже после `trade_till`, повторный `run_trade` не запускается и маркер не восстанавливается. Ветка missed считает день отторгованным, вахта О-3-Е полностью пропускается, а замыкание позже проходит через `traded_today`. Книга Е может остаться около 2× при запасе ниже 1,40 без среза и даже без тревоги. `status()` тем временем ещё и ложно пишет «торговля нет».  
   **Ложное доказательство:** зонд наблюдает только исправленную missed-ветку; оболочка и траектория до вахты стендами не исполняются.

3. **`live/ib_broker.py::IBBroker.preview` — аварийный выход всё ещё заперт при самом тяжёлом стрессе.**  
   До чтения плана стоит:
   ```python
   if _c is None or float(_c) < 1.0:
       return False
   ```
   Поэтому ветка «все приращения неположительны — разрешить разгрузку» недостижима при cushion `<1,0`. Параметр `emergency=True` здесь ничего не меняет. Три таких отказа дают POSTPONED/ABORT именно при фактическом маржинальном дефиците, оставляя маршрут Е без аварийного выхода.  
   **Ложное доказательство:** `SAME_API` проверяет «стресс» только на cushion `1,20`; ранний барьер `<1,0` не мутируется и не наблюдается.

4. **`live/ib_broker.py::IBBroker.unit_ref` и `IBBroker.gross` — точная дата предыдущей сессии не применяется к ZN.**  
   Для ETF/ES передаётся `expected_prev`, но обе ветки ZN вызывают:
   ```python
   yield_pct(self.ib, today)
   ```
   без ожидаемой даты. Более того, `gross()` читает доходность второй раз отдельно от полосы. `feed.closes` тогда допускает бар возрастом до пяти календарных дней: пятничный TNX во вторник проходит, старый `dref` размеряет ZN, а широкая полоса, построенная по столь же старому `dref`, это не ловит. `CLOSE_CAP=2,00` может пропустить фактически более крупную книгу.  
   **Ложное доказательство:** стаб всегда кладёт TNX ровно на ожидаемую дату; случая «конечный, правдоподобный, но на одну сессию старый» нет.

### P1 — поставка / недостижимое восстановление / рассинхронизация

5. **`live/session.py::do_trade` делает `live/daily.py::_resume_intent` недостижимой на заявленном пути восстановления.**  
   После смерти между `ST.save()` и `ST.clear_intent()` книга уже имеет сегодняшнюю дату и `close_provisional=True`. `do_trade` отказывает как штатный повтор **до** вызова `DL.run_session`, внутри которого находится `_resume_intent`. `do_close` одновременно запрещает замыкание при любом intent. Получается постоянный тупик: intent автоматически не разбирается, замыкание не идёт, следующая сессия и ролл заперты.  
   **Ложное доказательство:** сценарий «состояние уже дописано» вызывает `DL.run_session` напрямую и обходит именно тот `session.do_trade`, который делает защиту мёртвой.

6. **`live/daily.py::run_session` — потерянный журнал отмывается новой GENESIS в сессию без заявок.**  
   `J.verify`, проверка последней строки ИТОГ и запрет пустого журнала при `sess>0` находятся внутри:
   ```python
   if dec.trade and not dry_run:
   ```
   Но нулевая сессия всё равно строит `_pending_total` и вызывает `J.append`. Если у уже торговавшей книги удалить или обнулить журнал в день без ребаланса, код создаёт новую корректную цепочку с GENESIS и строкой «итог сессии N: строк 0». Следующая торговая сессия видит непустой валидный журнал и принимает утрату всей прежней истории как норму; WORM также заверяет новую цепочку.  
   **Ложное доказательство:** проверен только законный первый GENESIS у новой книги, а траектория `sess>0 + журнал утрачен + dec.trade=False` отсутствует.

7. **`live/daily.py::run_session` + `live/worm_anchor.py::_anchor_body` — разрыв между коммитом книги и ИТОГом заверяется как полная сессия.**  
   Порядок сейчас такой:
   ```text
   ST.save → ST.clear_intent → J.append(ИТОГ)
   ```
   Смерть после `clear_intent`, но до ИТОГа оставляет сегодняшнюю книгу без активного намерения. После перезапуска `do_trade` объявляет штатный повтор, `do_close` журнал не проверяет, а WORM проверяет только цепочку хэшей и непустоту — последнюю строку ИТОГ, её дату и номер против книги он не требует. В результате ставится `closed-*` и создаётся WORM-якорь для неполного журнала.  
   Для сессии без заявок разрыв ещё тише: последняя строка может оставаться ИТОГом предыдущего дня, и все проверки проходят. Это проверка после необратимого шага без механизма восстановления.

### P2 — порча и ложное заверение состояния

8. **`live/worm_anchor.py::_attested_paths` — обязательность журнала МР определяется его же текущим существованием.**  
   ```python
   _mr_live = _mrj.exists()
   ```
   Если действующий журнал МР был удалён, но deploy-конфигурация осталась, `_mr_live` становится `False`; и журнал, и deploy объявляются необязательными. `_anchor_body` также вызывает `_sha(_mr_journal())` без `required=True`. Снимок успешно заверяет утрату нормативного источника маршрута и одобрений как штатное отсутствие. Устойчивый признак «журнал раньше существовал» уже есть — deploy-файл, но код его не использует.  
   **Ложное доказательство:** стенд удаляет файлы, безусловно помеченные `required`; он не удаляет журнал при сохранившемся deploy.

9. **`live/worm_anchor.py::_tar_state` и `attested_missing_from_archive` — разыменование symlink исправлено только для внешнего списка, не для машинного состояния.**  
   Внешние `_attested_paths` кладутся через `_pp.resolve()`, но содержимое `.addfut` идёт обычным:
   ```python
   tf.add(p, ..., recursive=False)
   ```
   При стандартном `tarfile.dereference=False` `journal-*.csv`, `signals_live.csv`, `signals_levels.csv`, `account.txt` или `route.txt`, являющиеся symlink, попадут в архив ссылками. Проверка типа членов смотрит только `attested/...`, поэтому такой архив зелёный: якорь хэширует байты цели, а копия содержит лишь путь к ней. После потери машины восстановить байты невозможно. При внешнем `ADDFUT_SIGNALS` активный ряд вообще не входит ни в `.addfut`, ни в `_attested_paths`.  
   **Ложное доказательство:** symlink-стенд покрывает только специально добавленные внешние члены.

10. **`live/worm_anchor.py::_tar_state`, `anchors_without_archive`; `live/autopilot.sh::backup_state` — «поколение из имени» не имеет хронологического порядка и не уникально.**  
    Дата имени приходит из Чикаго, а время берётся в UTC:
    ```python
    addfut-{chicago_day}-{utc_HHMMSS}.tgz
    ```
    В 18:00 CST / 19:00 CDT UTC переходит через полночь, но чикагская дата ещё прежняя. Поздний архив `...-000100` лексикографически старше раннего `...-235900`. Ротация может удалить более новый снимок, а `anchors_without_archive` выбрать не последний якорь и пропустить свежий `.pending`.  
    Второй дефект того же имени: точность до секунды не уникальна. Два сериализованных `snap` в одну секунду перезапишут один `.tgz`; два WORM-якоря будут утверждать разные SHA для одного имени, а код противоречие не обнаруживает.

11. **`live/state.py::clear_intent` + `live/autopilot.sh::tick` — архивы намерений с collision-суффиксом не удаляются никогда.**  
    `clear_intent` специально создаёт:
    ```text
    intent-done-<epoch>-1.json
    ```
    если два снятия попали в одну секунду. Уборщик извлекает `epoch-1`, требует только цифры и делает `continue`. Все файлы, ради которых введён уникальный суффикс, выпадают из двухнедельной retention навсегда. При повторениях каталог состояния растёт до ENOSPC, после чего перестают писаться intent, книга, маркеры и тревоги.  
    **Ложное доказательство:** проверяется только базовое имя `intent-done-<epoch>.json`, не ветка уникализации самой производственной функции.

12. **`live/first_connect.py::main` — оператору выдаётся ложное подтверждение публикации, сама публикация недолговечна.**  
    При пустом или неполном whatIf код честно оставляет старый `margins_live.json`, но затем безусловно печатает:
    ```text
    записано: instruments_live.csv (...) и margins_live.json
    ```
    На описанном живом состоянии это прямо ложь: записан только реестр, замер оставлен прежним. Дополнительно ни CSV, ни JSON перед `os.replace` не fsync-ятся, и каталог после replace тоже не fsync-ится; даже настоящий «успех» не доказан против потери питания. После такого сообщения можно остаться без целевой серии перед роллом либо со старым поколением маржи, пока оператор считает обновление завершённым.
