## P0 — дефекты, способные прямо привести к неверной позиции, риску или изъятиям

### 1. Проверка CTD и коэффициента 0,88 методологически сломана

**`tools/ctd_basket.py`, основной блок выбора CTD:**

```python
ctd = o.loc[o['adj'].idxmin()]   # adj = P / cf
```

Минимум `цена/CF` не определяет CTD в общем случае. Нужны как минимум:

- текущая цена фьючерса;
- чистая цена бумаги и accrued interest;
- carry до поставки, купоны;
- repo specialness;
- net basis или implied repo.

Экономика поставки определяется величиной вроде `forward cash cost − futures_price × CF`, а не просто `P/CF`. Скрипт не загружает даже цену ZN, поэтому физически не может определить CTD.

Там же, `price_and_duration()`:

- считается грязная PV всех купонов, но accrued interest не отделён;
- денежные потоки короче года дисконтируются годовой ставкой из-за `np.interp(..., grid=1..10)`;
- результат назван модифицированной дюрацией, хотя это чувствительность к параллельному сдвигу непрерывно начисляемой zero curve;
- нет forward-оценки к месяцу поставки.

Финальная «подразумеваемая дюрация контракта»:

```python
ctd.D / ctd.cf * ctd.P / (ctd.P / ctd.cf)
```

алгебраически всегда равна `ctd.D`. Это не расчёт, а тавтология, замаскированная под проверку.

**Денежное следствие:** неверный CTD означает неверные DV01, число ZN, маржу и поведение книги при переключении CTD.

### 2. В `ctd_circularity.py` перевёрнут знак вывода о числе контрактов

**`tools/ctd_circularity.py`, печать результата после `c_star`:**

```python
(1 - c_star/S.CTD_RATIO)*100
```

По собственному выводу файла `N(c) ∝ 1/c`. Поэтому:

\[
\frac{N(0.88)}{N(c^*)}-1 = \frac{c^*}{0.88}-1,
\]

а код печатает величину с противоположным знаком.

Например, при `c*=0.787` фактическая книга с `c=0.88` меньше согласующей примерно на 10,6%, но код напечатает `+10,6%`. Следующая строка про экспозицию менее 100% будет противоречить предыдущей прямо в одном отчёте.

Ещё хуже, блок «что это стоит» меняет только:

```python
real = pnl / q
```

но затем вызывает `S.sim`, внутри которого округление контрактов, издержки, маржа и гранулярность по-прежнему считаются с замороженным `S.CTD_RATIO = 0.88`. То есть тест не моделирует главное последствие изменения `c` — другое число реальных контрактов. Он снова проверяет только масштаб доходности внутри той же модельной книги.

### 3. Режимная оценка дюрации использует доходности через пропущенные интервалы

**`tools/ctd_regimes.py`, блок «сводка по режимам»:**

```python
idx = zn.index[msk]
sub = zn.loc[idx]
r = np.log(sub['Close']).diff()[same]
```

После отбора только дней режима соседними строками `sub` могут стать даты, между которыми прошли дни или недели другого режима. `.diff()` тогда включает движение через исключённый промежуток, но вся доходность приписывается выбранному режиму.

То же происходит со ставкой:

```python
dy = y['SVENY07'].reindex(r.index).ffill().diff()
```

Это не условная дневная дюрация. В интервал фактически попадает движение кривой вне исследуемого режима. Сводные `k` выше/ниже условного купона поэтому загрязнены самим способом выборки.

Дополнительно регрессия доходности ZN на одну точку `SVENY07` не идентифицирует CTD-duration при непараллельных сдвигах кривой.

### 4. «Сверка с реальными фьючерсами» содержит явную ошибку календарной арифметики

**`tools/norgate_check.py`, раздел 4:**

```python
dt = expiry_key(codes[i + 1]) - expiry_key(codes[i])
dt = ((dt // 100) * 12 + dt % 100) / 12.0
```

Для перехода `2025Z → 2026H` ключи равны `202512` и `202603`. Разность — `91`, которую код превращает в `91/12 = 7,58 года` вместо трёх месяцев.

В том же файле:

- абсолютный календарный спред прямо признан не издержкой ролла, следовательно `ROLL_BP=1` скрипт вообще не валидирует.

### 5. `real_vs_model.py` не проверяет то, что заявлено в docstring

**`tools/real_vs_model.py`:**

```python
model_b = pd.Series(rb, index=days) - rf
model_a = pd.Series(re, index=days) - rf
```

Docstring утверждает, что модельная величина — `r − ставка − спред`, но спред в коде не вычитается.

Для ZN используется постоянное:

```python
q_b = S.ZN_MODEL_PX_EQ * S.CTD_RATIO
```

хотя заявленная модельная экспозиция содержит `D_fix/D_ref`. Центральная динамическая часть сайзинга выброшена с комментарием `D_fix≈D_ref`, но это и есть проверяемое допущение.

Также загружается `raw`, но нигде не используется. Не проверено, сохраняет ли конкретный тип back-adjustment Norgate абсолютное изменение цены, необходимое для:

```python
ZN_MULT * adj.diff()
```

Дни ролла не исключены и отдельно не исследованы. Наклон регрессии поэтому смешивает duration mismatch, кривую, basis, алгоритм склейки и календарь расчётов. Называть его проверкой коэффициента позиции нельзя.

### 6. В пакете нет единого движка: «одинаковая механика» взаимно противоречива

Одни и те же роллы тарифицируются по-разному:

- **только облигационная нога**:
  - `tools/smooth.py::sim` — `S.ROLL_BP * exp[1]`;
  - `tools/rebal.py::sim` — `S.ROLL_BP * exp[1]`;
  - `tools/putshield.py::sim` — `S.ROLL_BP * ex[1]`;
  - `tools/plot_position.py::run` — `S.ROLL_BP * exp[1]`.

- **обе ноги**:
  - `tools/legweights.py::sim` — `S.ROLL_BP*(exp_e+exp_b)`;
  - `tools/swr.py::run` — то же;
  - `tools/vd12.py::sim_vd12` — то же.

Обе конвенции не могут одновременно быть «как в ядре».

Есть и другие расхождения:

- в `tools/putshield.py::sim` нет полного cap-correction после округления и дрейфа;
- `tools/putshield_full.py::match` при выравнивании риска увеличивает сам кап до `cap*k`;
- часть файлов импортирует `r32build`, часть `pkg`, часть `run160`, часть `r33build`;
- `putshield.py`, `rebal.py`, `crossover.py` всё ещё используют полосу 3%, тогда как `r33-soprovoditelnaya.md` объявляет операционной полосу 10%.

Следовательно, сравнения надстроек не являются сравнением одного правила с одной заменой. Меняются одновременно стоимость ролла, кап, полоса и версия движка. Любой вывод о защитном путе, плавном входе, развесе или ребалансе может быть артефактом расхождения копий симулятора.

### 7. Хвост −58,5% получен не тем фильтром, который объявлен ядром

**`tools/signal_base.py::w_phase`:**

```python
on = v[i] > v[obs[k - LB:k]].mean()
```

Здесь текущая цена сравнивается с **12 предыдущими** наблюдениями.

В ядре и остальных скриптах используется:

```python
me > me.rolling(12).mean()
```

где текущая цена входит в 12-точечную среднюю. Условие

\[
x_t > (x_t+x_{t-1}+\dots+x_{t-11})/12
\]

эквивалентно сравнению с предыдущими **11**, а не 12 наблюдениями. `w_phase` тем самым добавляет ещё один период и начинает сигнал на период позже.

Дополнительно:

- `prep()` обрезает цены до `days`, поэтому фазовые варианты теряют предысторию и сначала сидят в нуле;
- наблюдения каждые 21 торговый день — это не «сдвиг календарного месяца»: календарные месяцы имеют разное число сессий, поэтому сетка постепенно уезжает относительно month-end.

Именно на эти результаты ссылается **`r33-soprovoditelnaya.md`, раздел «Бюджет просадки»**, устанавливая хвост −58,5%. Пока фазовый тест не повторён с идентичным окном, сохранённой предысторией и корректными датами, этот лимит не подтверждён.

### 8. Выводы об изъятиях получены не симуляцией денежных потоков стратегии

**`tools/withdrawals.py::with_draw`:**

```python
nav *= (1 + r.iloc[i])
...
nav -= w
```

`r` заранее получен из прогона без изъятий. Изъятия не возвращаются в движок и поэтому не меняют:

- число целых контрактов;
- попадание в полосу;
- cap-corrections;
- стоимость следующих сделок;
- гранулярность при уменьшении капитала.

Это особенно недопустимо именно в Депрессии, где пакет сам подчёркивает значимость кап-коррекций.

Конвенции также не являются безопасной нормой изъятия:

- «от текущего счёта» автоматически уменьшает потребление вместе с NAV и почти конструктивно не может обнулить положительный счёт;
- «от пика» привязана к номинальному пику, а не к CPI и не к постоянному реальному уровню жизни;
- просадка считается уже после потребления, смешивая инвестиционный убыток с добровольным выводом денег.

В **`r33-soprovoditelnaya.md`** написано: «4% от пика не выживают», но там же указан конечный капитал `×0,7`. Это не банкротство, а новое определение «не выжил» как «не вернулся к пику».

`tools/swr.py` действительно встраивает изъятия в симулятор, но работает только с 1963 года и только с январскими стартами. Он не закрывает заявление про 1929–1945 и 141-летнее окно.

### 9. История 1886–1962 содержит look-ahead, а не только заявленное сглаживание

**`tools/build_1885.py`:**

```python
yd = ycomb.reindex(...).interpolate('time').reindex(days_all)
```

Месячная средняя ставка Шиллера интерполируется между соседними месячными значениями. Доходность каждого дня внутри интервала зависит от следующего месячного наблюдения, которое тогда ещё не было известно. Это прямой look-ahead.

После этого синтетическая доходность:

```python
rb_syn = yd.shift(1) / 252 - dur.shift(1) * yd.diff()
```

используется и для P&L, и для сигнала. Получается стратегия, которая видит направление будущей месячной ставки, распределённое по дням. Оговорка о «заниженной качке» этот дефект не раскрывает.

Дополнительно:

- это лишь first-order duration approximation без convexity, roll-down и реального купонного календаря;
- `rb.fillna(0.0)` превращает пропуски в нулевую доходность и дополнительно сглаживает хвост;
- данные начинаются 20.03.1885, а `START=01.01.1886`: полного 12-месячного прогрева нет;
- отсутствие нулевых изменений никак не доказывает, что данные наблюдённые, а не интерполированные.

На этом ряду строятся хвосты, стресс-веса и выводы об изъятиях. Следовательно, «141 год» не равен 141 году независимых наблюдаемых дневных облигационных доходностей.

### 10. Стресс-тесты не генерируют заявленные сценарии

**`tools/stress.py::path_crash`:**

Базовая часть суммируется до заданной глубины, но затем к ней добавляются случайный шум, ралли и clipping:

```python
return np.clip(base + noise, ...)
```

После этого ни конечное падение, ни фактический минимум не обязаны соответствовать полю `depth`. Однако `stress_scenarios.csv` и `stress_weights.py` продолжают трактовать `depth` как реализованную глубину.

На каждую ячейку сетки приходится **один seed**. Различия между формами, сроками и поведением облигаций смешаны со случайной реализацией шума. Нет ни Monte Carlo, ни общих случайных чисел, ни доверительных интервалов.

Другие провалы:

- `CAP_MOVE=12%` специально исключает наблюдавшийся ход −20,4%, хотя текст ссылается на 1987 год;
- предварительные три года не проверяются на фактическое включение сигнала перед обвалом;
- спокойные ходы акций и облигаций независимы, что искусственно улучшает диверсификацию;
- восстановление случайно и не обязано восстанавливать рынок.

**`tools/stress_weights.py`** затем перемножает маргинальные частоты глубины, срока, формы и поведения облигаций. Для tail risk зависимость между этими признаками — не мелкая поправка, а центральный объект. Утверждение в docstring, что независимость «ослабляет, но не отменяет вывод», ничем не доказано.

### 11. «Сценарии премий» меняют не премию, а весь рискованный процесс

**`tools/scenarios.py::variant`:**

```python
rfv + k_eq * (re - rfv)
```

При `k=0` исчезает не только ожидаемая премия, но и вся волатильность, все обвалы и весь basis risk: нога превращается в детерминированный кэш. При `k=0.75` кризисы механически становятся на 25% мельче.

При этом сигналы оставлены историческими, хотя после изменения ценовой траектории moving average и состояния ног должны измениться. Получается невозможный контрфактический мир: доходности другие, а торговые решения сохранены от исходного мира.

Поэтому таблица «сценарии вперёд» не оценивает падение risk premium. Она одновременно уменьшает риск и дарит стратегии исторически удачные сигналы.

### 12. Вывод об отказе от защитного пута опирается на неправильный продукт и неправильный учёт

**`tools/putshield.py`:**

- underlying опциона — накопленный индекс **полной доходности**:

  ```python
  lvl = (1 + pd.Series(re, index=days)).cumprod()
  ```

  Реальные опционы торгуются на price index или фьючерс; для опциона на фьючерс нужен Black-76, а не применённый spot Black–Scholes без дивиденда.

- при выключении ноги оставшийся пут закрывается по intrinsic:

  ```python
  e += qty * max(K - lvl[i], 0.0) - pv
  ```

  Вся временная стоимость уничтожается, что систематически делает пут хуже;

- начальная 60-дневная волатильность заполняется из будущего через `.bfill()`;

- отсутствуют реальные option bid/ask, skew term structure, commissions и volatility jumps;

- нет полноценной cap-correction механики ядра.

**`tools/putshield_full.py::match`** дополнительно выравнивает риск, увеличивая допустимый кап:

```python
cap=cap * k
```

Это не сравнение при одном мандате: вариант с путом получает больше разрешённого плеча. На этой модели нельзя обосновывать фразу из `r33-soprovoditelnaya.md`, что защитный пут проверен и отклонён.

### 13. Анализ ликвидности систематически занижает участие книги в рынке

**`tools/roll_full.py`, раздел исполнимости:**

```python
vol = pd.concat([v['Volume'] for v in ...])
vol = vol.groupby(level=0).sum()
```

101 ZN и 26 ES сравниваются с суммарным объёмом **всей кривой контрактов**, хотя заявка исполняется в конкретной ближней или дальней серии. Это завышает доступную ликвидность и занижает participation rate.

Кроме того:

- используются трёхлетние медианы, скрывающие худшие дни и собственно дни ролла;
- фиксированная книга не отражает изменение числа контрактов с капиталом и CTD;
- не сравнивается отдельно ликвидность выходной и входной серий;
- market impact не моделируется.

**`tools/roll_check.py`:**

```python
later = [d for d in spec_rolls if d >= co - pd.Timedelta(days=40)]
sp = later[0]
```

может выбрать календарный ролл, который уже произошёл до OI-crossover. Тогда расчёт разрыва даст ноль вместо отрицательного значения. Для GC используется календарь `S.roll_days_calendar`, предназначенный не для шестимесячного/двухмесячного цикла GC.

Ни один из этих файлов не вычисляет фактическую стоимость сдвига ролла, хотя сопроводительная записка утверждает, что измеримая часть эффекта равна нулю.

Особенно опасно решение расширить полосу до 10%: записка сама признаёт принудительную сделку до 9,7% капитала в кризис. Модель издержек линейная и не содержит market impact, поэтому её вывод «доходность не изменилась» почти встроен в допущение.

### 16. В `smooth.py` есть скрытый look-ahead

**`tools/smooth.py::to_days`:**

```python
return ...shift(1).bfill()
```

Для облигационного ряда, начинающегося около 1962 года:

- ансамблю нужно 18 месяцев;
- наклону и логистике — минимум 60 месяцев.

Все начальные неопределённые дни заполняются первым будущим вычисленным весом. Комментарий «подсмотра вперёд нет» неверен: локальная оценка `s.shift(1)` использует прошлое, но затем результат распространяется назад на годы через `bfill()`.

Логистика также никогда не даёт ноль:

```python
1 / (1 + np.exp(-z))
```

Даже глубоко ниже средней нога формально остаётся включённой. Это не плавная версия бинарного выключателя, а другая стратегия.

### 17. Большинство сравнений использует псевдорепликацию вместо независимых окон

Это повторяется в:

- `tools/crossover.py::rolling_vs`;
- `tools/smooth.py`, блок 10-летних окон;
- `tools/fxhedge.py::rolling`.

Соседние 10-летние окна отличаются одним днём, то есть перекрываются на 2519 из 2520 наблюдений. Проценты вроде «впереди 63,4% окон» не означают тысячи независимых проверок. Эффективное число независимых десятилетий измеряется единицами.

Нет block bootstrap, HAC-ошибок, holdout-периода или коррекции за число кандидатов.

В `tools/crossover.py` дополнительно:

```python
table(... FAMILY_B ..., base_key=(3, 12))
```

помечает `3/12` как «ядро», хотя ядро — `1/12`. А выравнивание по среднему плечу не выравнивает ни волатильность, ни tail risk.

### 18. Тест сигнала по избыточной доходности снимает ограничение капа

**`tools/signal_excess.py::match`:**

```python
cap=2.0 * k
```

Кандидату разрешается большее максимальное плечо, чтобы догнать риск ядра. Это не проверка альтернативного сигнала при одном мандате.

Кроме того, `bases()` строит ценовые индексы только с начала уже обрезанного окна, поэтому `M.weights()` проходит новый 12-месячный прогрев и не воспроизводит исходную предысторию ядра. Регрессионной проверки равенства базового варианта здесь нет.

### 19. `q1_impact.py` не измеряет цену подмены на уровне счёта

Функция `leg()` игнорирует:

- целые контракты;
- полосу;
- стоимость переключений;
- роллы;
- cap-corrections.

После этого разница CAGR одной упрощённой ноги объявляется приблизительной разницей CAGR всего счёта:

```python
≈ {(c1-c2):+.2f} п.п.
```

Из-за совместной капитализации, другой ноги и издержек это не следует из расчёта. Подмена прокси как раз может увеличить число переключений, но стоимость этих переключений выкинута.

`tools/plot_bench.py`, `plot_candles.py`, `plot_equity_candles.py`, `plot_position.py` жёстко пишут **«ред. 32»**, хотя сопровождают пакет ред. 33 и часть из них импортирует старые деревья.

В `tools/plot_bench.py` бенчмарк:

```python
rb = pd.Series(d[1], index=days)
```

не платит никаких издержек входа, несмотря на подпись:

> «на том же окне и с теми же издержками входа».

Фильтр `n >= 200` принимает март–декабрь 1963 года как «полный год». Поэтому число прибыльных лет и свеча 1963 года подписаны неверно.

## P2 — целостность, воспроизводимость и прямой риск лишних расходов

### 21. `openai_review.py` не защищает от повторной оплаты

**`tools/openai_review.py::cmd_review`:**

- после падения на части 2 повторный `review` снова оплатит часть 1;
- реестр не ищется по хэшу входа;
- `resume` сохраняет одиночный ответ, но не восстанавливает `outs` и не продолжает сводный pipeline;
- нет idempotency key;
- нет блокировки `openai-jobs.json`, поэтому параллельные процессы могут потерять записи.

Кроме того, `_client()` не задаёт `max_retries=0`. Стандартный SDK сам повторяет часть 408/409/429/5xx и сетевых ошибок, вопреки заявлению «молчаливых повторов нет».

`create()` ловит только `APIStatusError`. Сетевой timeout после принятия запроса сервером может оставить платное задание без сохранённого `response_id`.

`parts_of()` не разбивает одиночный файл больше бюджета, а сводный запрос вообще не ограничен по размеру. `cmd_selftest()` в третьем тесте отправляет полноценную платную рецензию, хотя называет это тестом объёма.

Это уже не инвестиционный риск, а прямой риск повторных счетов API.

### 22. «Внешняя рецензия» не могла проверить эмпирические числа

**`tools/openai_review.py::collect`:**

- CSV больше 8000 байт исключаются;
- `.pkl`, PDF и прочие бинарные результаты исключаются;
- дубликаты по содержимому удаляются без учёта роли пути.

Следовательно, рецензент не видел основные временные ряды, фьючерсную историю и NAV. Он мог читать заявления и код, но не проверять опубликованные числа. Использование этих рецензий в `r33-soprovoditelnaya.md` как элемента уверенности в расчётах необоснованно.

Также нет защиты от prompt injection внутри рецензируемых файлов.

### 23. Заявленная схема хэша архива выглядит самоссылочной

В начале **`r33-soprovoditelnaya.md`** сказано, что SHA-256 ZIP:

> «продублировано в `docs/r33-sha256.txt`».

Если этот файл действительно находится внутри того же ZIP, он не может обычным способом содержать окончательный SHA-256 архива, частью которого является: изменение текста хэша меняет сам хэш ZIP. Нужен внешний detached hash или подпись, а не самоссылка внутри объекта.

### 24. PDF не является детерминированной сборкой

**`tools/make_spec_pdf.py`** не фиксирует:

- PDF metadata/CreationDate;
- версию Matplotlib;
- версию и конкретный файл шрифта;

Поэтому обещание «бинарного файла с устойчивым хэшем» не обеспечено кодом. `textwrap` с `break_long_words=False` также допускает выход длинной строки за страницу.

`tools/pdf_text.py` при неизвестном glyph просто возвращает пустую строку:

```python
mp.get(c, '')
```

и не завершает работу ошибкой. Такой извлекатель не годится как проверка полного round-trip текста.

## Прямые противоречия в `r33-soprovoditelnaya.md`

1. Заголовок говорит **«Семь решений заказчика»**, таблица содержит восемь решений.
2. Утверждение «все прогоны пройдены на настоящей редакции» не согласуется с массовыми импортами `r32build`, `pkg`, `run160` и графиками «ред. 32».
3. «4% не выживают» сопровождается конечным капиталом `×0,7`; это смена определения банкротства.
4. Сдвиг ролла объявлен измеренно бесполезным, но представленные `roll_check.py` и `roll_full.py` не считают его фактическую стоимость.
5. Защитный пут объявлен проверенным, хотя соответствующий симулятор использует неправильный underlying, неверное раннее закрытие и другой cap.
6. Полоса 10% выбрана по модели с линейными издержками, хотя сама записка признаёт кризисную разовую сделку 9,7% капитала — именно там линейная модель наиболее неправдоподобна.
7. Живой пилот 10% капитала ниже порога маршрута Ф, поэтому маршрут по умолчанию останется проверен только на paper account. Paper fills не проверяют ни проскальзывание, ни market impact, что записка сама признаёт.
8. Открыты `con_id`, супервизор, маржинальный, налоговый и фактический стоимостной контуры. Число 20 живых исполнений не даёт статистической проверки хвостов издержек или кризисной ликвидности.

## Что требуется пересчитать до использования чисел этой части

1. Один канонический движок вместо копий, с regression-тестом NAV **и книг** для каждой надстройки.
2. CTD по net basis/implied repo с реальными cash/futures quotes, accrued interest и exchange test vectors для CF.
3. Фазовый тест с точно тем же SMA, сохранённой предысторией и календарными датами.
4. Изъятия внутри полного контрактного симулятора, с CPI и всеми месяцами старта.
5. Историческую облигационную ногу без интерполяционного look-ahead.
6. Стресс-сценарии с контролем фактической глубины, множеством seed, совместной зависимостью ног и gap-сценариями хуже 12%.
7. Ликвидность по конкретным сериям и датам исполнения, а не по сумме всей кривой.
8. Идемпотентный платный API-workflow с хэшем запроса, checkpoint частей и отключёнными скрытыми retry.
