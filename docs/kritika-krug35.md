# Рецензия тридцать пятого круга ред. 33 (gpt-5.6-sol, pro+max)

### Неверная позиция / рассинхронизация с брокером

1. **[P0] `transition.py::_run_lots`, `_execute_locked.fail` — потерянное подтверждение первой заявки всё ещё может закончиться ложным `ABORT`.**  
   `st['order_ids'].append(oid)` выполняется только после возврата `sell_units()`/`buy_units()`. Если брокер исполнил заявку и соединение оборвалось до возврата, в состоянии нет ни `order_id`, ни `executed_usd`. В `fail()` пустой `_mine` заставляет проигнорировать все отчёты дня; при устойчиво старом снимке `moved == 0`, после чего пишется `ABORT` и снимаются handover-метки. Поздняя продажа затем приходит поверх старой книги, а автопилот уже вправе подать новый ребаланс — недобор либо short на величину заявки. Стенд `_BX` этого не доказывает: его позиция меняется немедленно, поэтому сценарий ловится по `moved`, а не новой сверкой отчётов.

2. **[P0] `live/daily.py::run_session`, `live/session.py::do_o3e_cut` — срез О-3-Е начинает двухногую операцию без запаса времени на пару.**  
   Перед первой заявкой среза вызывается `_window_gate(..., margin_min=False)`. Автопилот также проверяет только `now < trade_till`. Поэтому первая продажа CSPX может исполниться за секунды до края, а перед CBU0 уже сработает `WindowClosed`; затем `restore_to()` отправляет восстановительные GTC уже за краем окна. Денежный исход — непарная дельта порядка половины NLV или ночная заявка на закрытой европейской площадке. Начальный `margin_min=True` основной сессии не защищает пост-трейдовый срез: к нему могут пройти несколько 120-секундных ожиданий.

3. **[P0] `live/daily.py::run_session`, `live/session.py::do_trade` — «тревога до состояния» исправлена только для пост-трейдового среза.**  
   Предторговый срез выполняется внутри `step_e()` и выставляет `dec.o3e_cut`, но `o3e_alarm_fn` вызывается только во вложенной ветке второго, пост-трейдового среза. Для предторгового пути книга сохраняется, intent снимается, итог §7 пишется, и лишь после возврата из `run_session()` внешний `do_trade()` создаёт ALARM обычным `Path.write_text` без `fsync`. Возможен долговечный `traded-*` при потерянной тревоге; следующая полоса вернёт необъяснённо сокращённую книгу к 2x.  
   **Ложное доказательство:** мутация `o3e_cut_silent` патчит `session.post_o3e_alarm`, а не удаляет вызов `o3e_alarm_fn` в `daily.run_session`. Мутант, заменяющий именно восстановленный вызов на `pass`, останется зелёным: внешний код всё равно создаст файл к концу теста.

4. **[P1] `transition.py::_execute_locked.fail` — новая сверка отчётов логически инвертирована и не является сопоставлением идентификаторов.**  
   При наличии отчётов дня, но отсутствии отчётов этого перехода код пишет `_ex_note = 'НИ ОДИН не относится...'`, после чего выбирает:
   ```python
   kind = 'mixed' if (... or _ex_note) else 'abort'
   ```
   То есть доказанное отсутствие исполнений перехода само вызывает `MIXED`. Кроме того, используется `any(_m in str(e) ...)`: подстрока `"12"` совпадёт с чужим `permId=9123`, а локальный `orderId` вообще не равен `permId`. Чистый нулевой fill после утреннего ребаланса оставит pending и обе handover-метки; ежедневная торговля и замыкание заблокируются, фьючерсная книга может пропустить ролл и войти в поставочную зону. Это не открытый долг обычного intent — дефект находится именно в заявленной исправленной ветке перехода.

5. **[P2] `live/daily.py::run_session` — после успешного пост-трейдового О-3-Е объект `Decision` остаётся внутренне ложным.**  
   Код меняет только `dec.book_after` и `dec.o3e_cut`. `dec.orders`, `dec.exposure`, `dec.leverage`, `dec.capital_after_costs` и `dec.daily_costs` остаются от книги до среза; возвращаемый список `orders` также не содержит заявок среза. В результате §7 получает старое плечо, расчёт займа/дебета относится к уже проданной книге, а операторский лог скрывает крупнейшие исполнения дня. Проверки смотрят на сохранённую книгу и `o3e_cut`, поэтому это противоречие не наблюдают — ложное доказательство достижения L=1 на уровне результата функции.

### Поставка / остановка управления

6. **[P1] `transition.py::_drop_handover`, `_mark_handover`, `_execute_locked` — ошибки снятия меток всё ещё выбрасываются в нескольких точках.**  
   Возвращаемое `_drop_handover()` значение игнорируется:
   - в обработчике ошибки `_mark_handover()`;
   - при исключении из `hook('open')`;
   - когда `hook('open')` вернул `False`.
   
   При этом `_drop_handover()` очищает исходный список даже при неудачном `unlink/fsync`. Если первая из двух меток создана, а создание второй или OPEN отказали, оставшаяся метка не называется и ALARM не ставится. Сессии обоих маршрутов затем запрещают торговлю и замыкание; на Ф это прямой путь к пропущенному роллу и поставке.

7. **[P1] `live/autopilot.sh::env_guard`, `trade_till` и сторож занятого lock — заявление о переводе всех ALARM-записей на `alarm_write` ложно.**  
   Остались непроверенные записи:
   ```bash
   { ...; } > "$ST/ALARM-lock.txt"
   echo ... > "$ST/ALARM-env-....txt"
   echo ... > "$ST/ALARM-calendar-window.txt"
   ```
   Особенно опасен сторож lock: после неудачной записи он всё равно делает `exit 0`. При ACL «существующий lock открывать можно, новый ALARM создавать нельзя» каждый cron выглядит успешным, но ни ребаланса, ни ролла нет, а `status` способен показать «тревог нет». `env_guard` аналогично останавливает каждый тик без долговечного ALARM/STOP.

### Порча состояния и ложные доказательства

8. **[P1] `live/worm_anchor.py::reject_archive` — переименование отвергнутого архива не fsync’ит каталог.**  
   `rename(...tgz -> ...tgz.rejected)` возвращается как успех без `fsync(dst.parent)`. После потери питания каталог может восстановить старое рабочее имя `.tgz`, хотя код уже установил, что архив разных поколений либо не имеет подтверждённого якоря. Следующий `backup_push.sh` подхватит его как штатную копию; восстановление из неё даст старую книгу при другой позиции брокера и последующие дубли. Немедленная проверка имени в стенде долговечность rename не доказывает.

9. **[P2] `live/journal.py::rows_from_decision.emit` — пропорциональность ролла исправлена только когда вся ролловая часть меньше одного ES, но не для дробного остатка после целых ES.**  
   При старой упаковке `2 ES`, новой экспозиции `15 MES` и ролловом пуле `15` код получает:
   ```python
   q_roll = int(15 // 10) = 1
   ```
   и относит к роллу только 10 единиц; оставшиеся 5 в закрывающей стороне исчезают из роллового класса. Нужно `1.5 ES` ролловой строки и `0.5 ES` обычной. Сейчас односторонний ролловый номинал занижается, ставка §7 завышается и после двадцати наблюдений может дать денежно неверное основание менять 1 б.п.

10. **[P2] `live/mutation.py::_j7_mutations.roll_sub_lot_zero` — парная мутация пропорции фактически ничего не мутирует.**  
    Условие:
    ```python
    abs(int(float(r['qty']))) == 1
    ```
    ложно для новой ролловой строки `qty=-0.5`: `int(-0.5) == 0`. Поэтому пометка не снимается, выход функции не меняется, а прогон либо объявит мутацию непойманной, либо поймает что-то постороннее. Это прямое ложное доказательство правки 34-го круга; кроме того, сам стенд покрывает только `0.5 из 1 ES`, не случай `1.5 из 2 ES`, где производственный дефект остаётся.

11. **[P2] `live/invariants.py::_adapter/_a33e`, `live/mutation.py::etf_expect_off` — стенд не проверяет новую привязку класса фонда к имени.**  
    Сценарий `etf_line_swap` меняет только `primaryExchange`; строки реестра CSPX/CBU0 всё равно имеют `sec_type='STK'`. Мутация удаляет весь `etf_expectation_bad`, но не воспроизводит прежний дефект:
    ```python
    if row['sec_type'] != 'STK':
        return []
    ```
    Регрессия именно к этому раннему выходу пройдёт все текущие случаи, потому что ни один не подменяет одновременно строку и ответ биржи на FUT/CFD. Денежный путь прежний: цена фьючерса размеряет «доли CBU0», после чего исполнитель отправляет тысячи контрактов вместо долей ETF. Заявленная парная мутация класса фонда этого не доказывает.
