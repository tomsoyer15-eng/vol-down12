# Рецензия седьмого круга ред. 33 (gpt-5.6-sol, pro)

Ниже — дефекты, а не пересказ. Сначала те, что способны дать неверную фактическую позицию или сорвать синхронизацию.

## 1. Критично: позиции всех managed accounts смешиваются, после чего заявки идут только в один account

**Файл:** `live/ib_broker.py`  
**Функции:** `IBBroker._snapshot()`, `IBBroker.net_positions()`, `IBBroker.__init__()`

```python
pos = self.ib.reqPositions()
return {p.contract.conId: float(p.position) for p in (pos or []) if p.position}
```

`reqPositions()` у IBKR возвращает позиции по всем доступным счетам. Поле `p.account` игнорируется. При одинаковом `conId` на нескольких счетах dict comprehension не суммирует и не фильтрует — побеждает последняя строка.

При этом заявки получают:

```python
o.account = self.account
```

То есть сверяется случайный/чужой счёт, а торгуется `self.account`.

Денежный сценарий:

- на целевом счёте 0 ES;
- на другом managed account 26 ES;
- `_snapshot()` сообщает 26 ES;
- сверка с состоянием проходит;
- система считает, что на торговом счёте позиция уже есть, и не покупает её либо подаёт неправильную дельту.

**Почему доказательства ложны:** `live/ib_stub.py:StubIB.positions()` вообще не содержит `account`; подстановка по построению моделирует только один счёт. Все проверки адаптера гарантированно не видят этот класс.

## 2. Критично: восстановленное намерение ролла немедленно запускает второй ролл в следующую серию

**Файл:** `live/daily.py`  
**Функции:** `_resume_intent()`, `run_session()`, `step()`, `target_tag()`

Если процесс умер после полностью исполненного ролла, `_resume_intent()` принимает `book_after`:

```python
ST.save(bp, after, route, sess + 1, ...)
return after
```

Но затем `run_session()` не завершает восстановленную сессию, а продолжает обрабатывать тот же `market`:

```python
book = _resume_intent(...)
...
dec = step(book, market, ...)
```

Для дня ролла `market.roll_today=True`. Уже принятая книга `Z26` снова проходит:

```python
target_tag('Z26', ..., roll_today=True) -> 'H27'
```

Итого после обрыва между сделкой и записью:

1. фактически исполнен `U26 -> Z26`;
2. перезапуск принимает `Z26`;
3. тот же запуск строит второй ролл `Z26 -> H27`.

Это прямой уход на квартал вперёд.

**Ложное доказательство:** `live/invariants.py:_intent_case()` вызывает только `_resume_intent()` и проверяет, что `after` принят. Полный `run_session()` после принятия намерения не запускается. Самая опасная часть последовательности отсутствует по построению.

## 3. Критично: исправление дробных ETF не дошло до полного переходного исполнителя

**Файл:** `transition.py`  
**Функции:** `_execute_locked()`, `_run_lots()`, `target_book()`

### 3.1. Законная дробная позиция ETF отвергается до первой заявки

```python
if snap0.get(instr, 0) != int(units):
    raise Incident(...)
```

Для `CBU0 = 2_000_000.5` сравнивается:

```text
2_000_000.5 != 2_000_000
```

Переход `E -> F` невозможен, несмотря на заявленное исправление в `plan_lots()`.

### 3.2. Если этот барьер убрать, последний дробный лот округляется вверх и создаёт short

В `_run_lots()`:

```python
remaining = lot['units']
...
step = max(1, min(remaining, int(...), int(...)))
```

При `remaining == 0.5` получается `step == 1`. Исполнитель продаёт одну долю вместо половины и уводит источник на `-0.5`.

### 3.3. Предстартовая маржа тоже усекает дробь

```python
usd = sum(int(u) * float(uu) for _, u, uu in spec['src'])
```

`target_book()` считает целевую книгу не из фактических `2_000_000.5`, а из `2_000_000`.

**Ложное доказательство:** `live/invariants.py:_t2` проверяет только:

```python
sum(l['units'] for l in lots) == 2_000_000.5
```

Дробный план никогда не прогоняется через `_execute_locked()` и `_run_lots()`. Проверен планировщик, а заявлено выполнение перехода.

## 4. Критично: переходный исполнитель и ежедневный контур по умолчанию всё ещё пишут разные книги

**Файлы:** `transition.py`, `live/session.py`  
**Функции:** `transition._execute_locked()`, `session._book_path()`

Ежедневный контур по умолчанию читает:

```python
~/.addfut/book-F.json
~/.addfut/book-E.json
```

Переход после исполнения пишет:

```python
_bp = ADDFUT_BOOK_PATH or ~/.addfut/book.json
```

Отдельный процесс `transition.py` не наследует переменную, которую `session.do_trade()` установил внутри другого процесса.

Итог без вручную заданного глобального `ADDFUT_BOOK_PATH`:

- брокер уже переведён в маршрут E;
- `transition.py` сохраняет новую книгу в `book.json`;
- ежедневный запуск читает старую `book-F.json`;
- источник истины снова раздвоен.

Следующая сессия, вероятно, остановится на сверке, но штатного продолжения после перехода нет. Если старые и новые позиции частично совпадут, возможна неверная реконструкция намерения.

**Ложное доказательство:** переходные инварианты вызывают только `plan_lots()` и `_run_lots()`. Полный путь до передачи книги ежедневному контуру вообще не проверяется.

## 5. Критично: `--close` читает состояние вне блокировки и может затереть книгу после перехода

**Файл:** `live/session.py`  
**Функция:** `do_close()`

Порядок:

```python
book, sess, saved = ST.load(bp, cls)       # без lock
nav = br.net_liquidation()                 # без lock
closing_values(...)                        # без lock
closed = finalize_close(...)
with ST.hold_book_lock():
    ST.save(bp, closed, ...)
```

Между `load()` и захватом lock переходный исполнитель может:

1. захватить общий lock;
2. завершить перевод маршрута;
3. сохранить новую книгу;
4. освободить lock.

После этого `do_close()` захватывает lock и без повторного чтения записывает поверх неё старую книгу.

Это классическая потерянная запись с фактической позицией уже на другом маршруте.

Дополнительно `saved` вообще не проверяется против `route`.

**Почему проверки не видят:** сценарий `invariants._session_run('замыкание')` однопоточный; конкурентного перехода между чтением и записью нет.

## 6. Высокий: замыкание можно повторить или выполнить за чужую дату, переписав триггер капа

**Файлы:** `live/session.py`, `live/feed.py`  
**Функции:** `do_close()`, `closing_values()`

`do_close()` не проверяет:

- что `book.close_provisional is True`;
- что `book.last_session` совпадает с датой закрываемой сессии;
- что замыкание ещё не выполнялось.

Если замыкание пропущено в понедельник и оператор запускает `--close` во вторник после 16:00, берутся вторничные цены и вторничный NLV, но ими замыкается книга с `last_session='понедельник'`.

Повторный `--close` в следующую дату снова перепишет `prev_close_lev`.

Результат — кап следующей сессии срабатывает по плечу не того закрытия. Это молчаливая смена стратегии.

**Ложное доказательство:** `_r6` проверяет один успешный вызов и только факт `provisional=False`; повтор и разрыв дат отсутствуют.

## 7. Высокий: отчёт `late_fills` якобы проверяет барьер `reqExecutions`, но проходит без него

**Файлы:** `live/ib_broker.py`, `live/ib_stub.py`, `live/invariants.py`  
**Функции:** `IBBroker._executed()`, `IBBroker.place()`, `StubIB.placeOrder()`, `_a8()`

Для терминального `Filled` адаптер не вызывает `_exec_barrier()`:

```python
if st in TERMINAL_OK:
    self.ib.sleep(1.0)
    return self._rec(...)
```

В сценарии `late_fills` отчёт лежит в `_pending` и должен появиться только после `reqExecutions()`. Но `_executed()` делает запасной ход:

```python
return float(tr.orderStatus.filled or 0) * sign
```

У подстановки `orderStatus.filled == 2`, поэтому проверка:

```python
r['filled'] == 2
```

проходит, хотя `reqExecutions()` не вызывался вообще.

Это ровно требуемое ложное доказательство: название утверждает «отчёт, приходящий только по запросу, не теряется», а факт запроса не проверяется.

Сценарий `late_cancelled` частично маскирует дыру, потому что там специально выставлен нулевой счётчик статуса. Но обычный `late_fills` ничего не доказывает.

## 8. Высокий: сопоставление по `permId` фактически необязательно

**Файл:** `live/ib_broker.py`  
**Функция:** `IBBroker._executed()`

Комментарий обещает:

> Пока permId не присвоен, исполнения не засчитываются вовсе.

Код делает обратное:

```python
if perm:
    ... поиск по permId/contract/account ...
    if n:
        return n
return float(tr.orderStatus.filled or 0) * sign
```

Запасной путь применяется и когда:

- `permId == 0`;
- отчётов с этим `permId` нет;
- отчёт найден, но контракт не совпал;
- отчёт найден, но счёт не совпал.

То есть проверка личности исполнения может не пройти, а исполнение всё равно будет принято из статуса.

Подстановка не содержит сценария «есть только чужой fill, а собственный `orderStatus.filled` ненулевой». В `foreign_fill` она одновременно добавляет и корректный собственный fill, поэтому проверяется удобный случай, а не отказ при отсутствии доказательства.

Отдельно комиссия снова сопоставляется только по `orderId`:

```python
if f.execution.orderId == tr.order.orderId
```

Заявленное устранение коллизии `orderId` не доведено даже до всей записи исполнения.

## 9. Высокий: подстановка врёт о достижимости окончательной позиции после барьеров

**Файлы:** `live/ib_broker.py`, `live/ib_stub.py`  
**Функции:** `IBBroker._exec_barrier()`, `IBBroker.refresh()`, `StubIB.reqExecutions()`, `StubIB.reqPositions()`

В реальности:

- `execDetailsEnd` завершает конкретный ответ `reqExecutions`;
- он не гарантирует, что позднее исполнение открытой/отменяемой заявки уже невозможно;
- сервис позиций может отставать от сервиса executions;
- два одинаковых снимка могут быть двумя одинаково устаревшими снимками.

Код тем не менее принимает два совпавших снимка как истину:

```python
if cur == prev:
    self._stable = cur
    return cur
```

Подстановка моделирует только «отставание ровно на один запрос»:

```python
if behaviour != 'stale_positions' or self._pos_reads > 1:
    self._shown = self._pos
```

По построению второй запрос всегда исцеляет состояние. Нет сценариев:

- два или больше одинаковых устаревших снимка;
- исполнение приходит после `execDetailsEnd`;
- `reqExecutions()` завершился, а позиционная выгрузка ещё старая;
- отменённая заявка исполняется после успешного восстановления.

Следовательно, «совпали два снимка» не является барьером IBKR, а тест лишь воспроизводит алгоритм, под который написан код.

## 10. Высокий: сборщик цен не выполняет новую проверку личности контракта

**Файлы:** `live/feed.py`, `live/ib_broker.py`  
**Функции:** `feed.contract_of()`, `IBBroker._contract()`

Торговый адаптер сверяет expiry, multiplier и local symbol. Сборщик входов — нет:

```python
c = Contract(conId=int(reg[name]['con_id']))
ib.qualifyContracts(c)
if not c.conId:
    ...
return c
```

Если в реестре имя `ESZ26` ошибочно связано с валидным `conId` другой серии, `feed` возьмёт цену чужого контракта и на ней рассчитает размер книги. Позже `IBBroker._contract()` может отказать, но решение, причины, ориентиры и ролловая логика уже построены по другому активу.

Исправление «con_id принимается только после сверки поставки и множителя» действует только на подачу заявки, а не на денежный вход расчёта.

Сценарий `wrong_contract` проверяет только `IBBroker`, не `feed.contract_of()`.

## 11. Средне-высокий: `first_connect` обходит исправленный праздничный календарь

**Файл:** `live/first_connect.py`  
**Функции:** `next_two_expiries()`, `main()`

```python
today = pd.Timestamp.today().normalize()
...
if DL.roll_passed_for(today):
```

Проблемы сразу две:

1. дата берётся в часовой зоне машины, не биржи;
2. `roll_passed_for()` вызывается без `holidays_for()`.

В ноябре 2026 фактический ролл сдвинут на 24 ноября. На 25 ноября функция без праздников считает, что её пятидневочный ролл ещё не прошёл, и может сформировать реестр начиная с уходящей серии.

То есть новая праздничная защита есть в `feed`, но генератор реестра, от которого зависит возможность подать заявку, её обходит.

Проверок `first_connect.next_two_expiries()` вокруг Thanksgiving нет вообще.

## 12. Ложная мутация: «даты баров не проверяются» ловится запасным отказом и поиском подстроки

**Файлы:** `live/mutation.py`, `live/invariants.py`  
**Функции:** `_feed_mutations().no_date_check`, `_feed_run()`, `_f3()`

Мутация удаляет проверку давности внутри `closes()`. Но сценарий делает старым только ES, оставляя TNX свежим. Поэтому сборщик всё равно падает на другой защите — несовпадении дат источников.

Инвариант требует конкретную подстроку:

```python
return r['m'] is None and 'отстал' in r['err']
```

Мутация объявляется «пойманной» лишь потому, что сообщение стало «даты не совпадают», а не «отстал». Опасный вход по-прежнему отвергнут.

При действительно нужном сценарии — **оба источника одинаково устарели на одну дату** — после мутации:

- даты ES и TNX совпадут;
- межисточниковая сверка пройдёт;
- старые входы будут приняты.

Такого состояния в `FEED_CASES` нет. Это одновременно:

- мутация, не открывающая опасный путь в имеющемся сценарии;
- ложная «пойманность» по тексту сообщения;
- пропуск пространства состояний по построению.

## 13. Перебор принципиально не проверяет многосессионные последовательности

**Файл:** `live/invariants.py`  
**Функции:** `states()`, `run_sessions()`, `_intent_case()`, `_session_run()`

Все основные проверки одношаговые. Отсутствуют последовательности:

- полностью исполненный ролл → падение до сохранения → перезапуск в тот же день;
- неудачный ролл в пятницу → `roll_pending` через выходные/праздник;
- пропущенное замыкание → `--close` на следующий торговый день;
- повторный `--close`;
- переход между маршрутами между чтением книги и её замыканием;
- переход посреди отложенного ролла;
- два одинаково устаревших снимка позиций;
- позднее исполнение после того, как восстановление уже объявлено успешным.

Ненулевое покрытие здесь ничего не означает: пространство не содержит временной оси, на которой находятся самые дорогие дефекты.

## 14. Журнал дважды списывает комиссию при разбиении одной заявки на ролл и обычную сделку

**Файл:** `live/journal.py`  
**Функция:** `rows_from_decision()`

Когда заявка новой серии содержит одновременно перенос и изменение размера, она разбивается на две строки:

```python
out.append(dict(base, ..., qty=q_roll, ...))
...
out.append(dict(base, ..., qty=rest, ...))
```

Но `base` в обе строки копирует полную комиссию исходного fill:

```python
commission=f.get('commission', '')
```

Комиссия одной биржевой заявки учитывается дважды. Сверка §7 систематически завышает фактические издержки именно в сессиях «ролл + изменение экспозиции».

Тест журнала создаёт по одной строке на отдельную заявку и этот путь не выполняет.

### Наиболее опасные исправления перед следующим запуском

1. Фильтровать позиции по `p.account == self.account`, а дубликаты `conId` не перетирать.
2. После принятия полностью исполненного намерения завершать прежнюю сессию отдельно; не повторно вызывать `step()` с тем же `roll_today`.
3. Прогнать дробный ETF через полный `transition.execute()`, убрать все `int(units)` и исправить последний `remaining < 1`.
4. Сделать единый обязательный путь книги для `session.py` и `transition.py`.
5. Держать book-lock на всём `do_close()` и повторно сверять книгу/маршрут перед записью.
6. Проверять `last_session == exchange_today()` и `close_provisional=True` перед замыканием.
7. Добавить сценарии: два счёта, оба источника одинаково устарели, два устаревших position snapshot, полный roll-intent recovery и повторное замыкание.
