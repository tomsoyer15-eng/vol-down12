# Рецензия тридцать девятого круга ред. 33 (gpt-5.6-sol, pro+max)

1. **[P0 — неверная позиция] `transition.py`, `_execute_locked`: `resume=True` разрешён без файла прогресса.**  
   При отсутствующем или ошибочно указанном `state_path` код создаёт новое состояние со `snapshot` уже промежуточной книги:
   ```python
   else:
       _snap_base, _ = _snapshot_pair(broker)
       st = dict(..., snapshot=_snap_base, ...)
   ```
   Затем resume видит нулевой прогресс и исполняет весь план повторно. Уже проданная часть продаётся ещё раз, вплоть до short источника. Финальная сверка считает дельту от нового ложного snapshot, поэтому способна признать повторное исполнение соответствующим плану; gross обнаружит лишь часть случаев и уже после лишних сделок. `resume` без существующего состояния с валидным digest должен немедленно давать MIXED/О-5. Путь прогресса также должен быть пинован, а не приниматься аргументом на веру.

2. **[P0 — неверная позиция/маржин-колл] `live/ib_broker.py`, `IBBroker.preview`: сумма `initMarginChange` не является маржой целевой книги.**  
   Каждый `whatIfOrder` считается отдельно против всё ещё существующей исходной позиции. Код складывает изменения:
   ```python
   _need += _im
   return _nlv / _need >= O3E_MIN
   ```
   Но `_need` — не `FullInitMarginReq` цели и даже не маржа портфеля после всех заявок. Неттинг с активами, которые затем будут проданы, загрязняет каждое приращение. Исправлен только случай `_need <= 0`; смесь отрицательных и положительных приращений с положительной суммой по-прежнему даёт ложное разрешение. Даже сумма только положительных `initMarginChange` остаётся изменением, а не полным требованием. Такой preview может пропустить переход в книгу, для которой после ликвидации источника запаса 1,40 уже нет.

3. **[P1 — неверная позиция] `live/daily.py`, `step` / `repack_excess`: канонизация ES/MES на ролле ошибочно считается дополнительной перекладкой.**  
   `pack_es(..., roll_a=True)` намеренно канонизирует упаковку на ролле; в описании `Book` прямо сказано, что эта канонизация на ролле бесплатна. Но затем `repack_excess()` приводит серии к одной и видит, например, `19 MES -> 1 ES + 9 MES` как лишний оборот. Возникают ложная причина `ИЗБЫТОК ОБОРОТА...` и, у границы капа, дополнительный cap-срез по фиктивному расходу. Результат — недобранная позиция после штатного ролла. Инвариант `_i12a` скрывает дефект условием `book_after.es_held == b.es_held`, то есть исключает именно роллы со сменой упаковки.

4. **[P0 — поставка/недостижимый выход] `transition.py`, `_preflight_handover`: производственный resume Е→Ф с ZN недостижим.**  
   Правка resume делает:
   ```python
   if _resume:
       _broker_p = None
   ```
   Ниже тот же `_broker_p` нужен для получения свежей доходности и `d_fix`:
   ```python
   _y, _yd = yield_pct(_broker_p.ib, ...)
   ```
   Поэтому запрос гарантированно падает, `_dfx_ok=False`, а при целевом ZN следует жёсткий отказ. Частично исполненный Е→Ф нельзя штатно продолжить; промежуточная книга остаётся разорванной. «Честный resume» в selfcheck проверяет только Ф→Е, где эта ветка `d_fix` отсутствует. Нужно отключать лишь сверку позиций, а не уничтожать ссылку на брокера.

5. **[P1 — поставка/порча намерения] `live/daily.py`, `run_session`, ветка `execute_roll`: чистый отказ окна ролла не снимает intent.**  
   `execute_roll()` возвращает `RollGap(provable=True)` при отказе ворот до первой заявки. Обработчик сохраняет `roll_pending`, увеличивает `session_no`, но `ST.clear_intent(bp)` не вызывает:
   ```python
   if gap.provable:
       ST.save(... roll_pending=...)
   raise
   ```
   На диске остаётся намерение сделки, которой не было. Оно блокирует замыкание и последующие запуски, а номер «завершённой» сессии уже увеличен. Кроме того, `provable` смешивает два разных исхода: чистый отказ и реально начатый, затем восстановленный ролл; вызывающий структурно не может понять, когда intent разрешено снять.

6. **[P1 — поставка] `transition.py`, вложенная `_mark_handover`: неудачный fsync оставляет вечную метку, которую уборка не знает.**  
   Файл добавляется в `_hoflags` только после записи и обоих fsync:
   ```python
   _f.write_text(...)
   fsync(file)
   fsync(dir)
   _hoflags.append(_f)
   ```
   Если файл уже создан, но fsync файла или каталога падает, путь ещё не находится в списке. `_drop_handover(_hoflags)` его не удалит, `_left_m` окажется пустым, а сообщение заявит чистый отказ. Оставшаяся `handover-inflight-*` навсегда запрещает торговлю и замыкание, включая ролл у поставки.

7. **[P0 — рассинхронизация] `transition.py`, `_execute_guarded` / `_execute_locked`: существующий `TRANSITION_OPEN` не считается аварией, а его файловый барьер может быть удалён.**  
   Начальный `derive_state()` возвращает `open_tid`, но код проверяет только MIXED и anomalies. Для чужого открытого tid новый запуск доходит до `_mark_handover()`, затем `hook('open')` возвращает False, после чего новые или прежние handover-метки удаляются как при «чистом отказе». Нормативный журнал остаётся в OPEN, а единственный барьер, читаемый ежедневным контуром, исчезает.  
   Selfcheck прямо закрепляет это как норму сценарием:
   > «чистый отказ OPEN не оставляет меток»  
   хотя фикстура заранее содержит `TRANSITION_OPEN ... ЧУЖОЙ-tid`. Старый OPEN не доказывает отсутствие прошлых заявок; это не чистый отказ, а О-5.

8. **[P1 — рассинхронизация/ложное доказательство] `live/daily.py`, `execute_roll.bail` и чистые ветки окон: утверждение «книга не менялась» не доказано.**  
   В ролле сверка снова выполнена опасным порядком:
   ```python
   broker.net_positions(), broker.open_orders()
   ```
   Если старая заявка исполнится между вызовами, будут приняты старая позиция и уже пустой список заявок; исход объявится `provable=True`. Нужно использовать `_snapshot_consistent`.  
   В обычном цикле и обоих циклах О-3-Е фактической сверки вообще нет, но сообщения утверждают «книга не менялась» или «осталась досрезной». Доказан только факт, что текущий вызов `place()` не состоялся; поздний fill или ручная сделка в этом окне не исключены.

9. **[P0 — порча состояния/блокировка капа] `live/daily.py`, `run_session`, чистый отказ ворот пост-трейдового О-3-Е: ошибка снятия intent проглатывается.**  
   ```python
   try:
       ST.clear_intent(bp)
   except Exception:
       pass
   raise RuntimeError(... намерение снято ...)
   ```
   К этому моменту книга после основных заявок уже сохранена как `_mid` и должна быть замкнута. При ACL/I/O/fsync-ошибке intent остаётся, но сообщение лжёт. `do_close()` затем отказывает из-за незавершённого намерения, поэтому фактическое закрытие и триггер капа следующей сессии не фиксируются. Стенд края окна проверяет только успешный `clear_intent`, а этот денежный исход не воспроизводит.

10. **[P0 — порча состояния] `live/autopilot.sh`, `tick`: STOP всё ещё допускает замыкание в том же тике.**  
    После `run_trade` стоит объединённая проверка:
    ```bash
    if ls .../ALARM-*.txt || [ -e autopilot.STOP ]; then
        ...
        ensure_gw && run_close
        return
    fi
    ```
    Внутри не различаются обычный ALARM и STOP. Если STOP появился во время `run_trade`, `traded_today` истинно — и `run_close` финализирует книгу, снимает backup/WORM и позволяет `closed-*` именно под признаком «состояние контура недоказуемо». Нижняя отдельная проверка STOP недостижима, потому что эта ветка уже сделала `return`. Заявление «STOP перечитывается перед замыканием и запрещает его» ложно для самого важного same-tick пути.

11. **[P0 — ложное сообщение о позиции] `live/session.py`, `_alarm_o3e`: отказ записи тревоги всегда утверждает, что срез исполнен.**  
    Ветка исключения заканчивается текстом:
    ```python
    заявки среза уже исполнены
    ```
    независимо от `done`. Но `done=False` используется до расчёта и подачи пост-трейдового среза и при неизвестном запасе. Более того, исключение из `_alarm_o3e` само прекращает выполнение до заявок. Оператор получает ровно противоположное факту сообщение и может не выполнить необходимое ручное сокращение.

12. **[P1 — ЛОЖНОЕ ДОКАЗАТЕЛЬСТВО] `live/ib_broker.py`, `SAME_API`; `live/fake_broker.py`: успешный preview живого адаптера не исполняется, поведение брокеров не сравнивается.**  
    У `_tl_pos` пустая позиция, поэтому `margin_cushion()` возвращает `None`, а оба вызова `preview` заканчиваются до `whatIfOrder`. Проверяется только `isinstance(..., bool)`, причём значения live и fake даже не сравниваются: live возвращает False, fake — True, а SAME_API остаётся зелёным. Отдельный `_tib_q` проверяет лишь отказ на пустом whatIf.  
    Поэтому не наблюдаются:
    - успешный положительный whatIf;
    - отрицательные и смешанные приращения;
    - привязка `order.account`;
    - округление фьючерса;
    - отказ по реальному недостатку запаса.  
    Аналогично `FakeBroker.gross()` игнорирует `d_fix`, а проверка удвоения `d_fix` выполняется только для live `_bz`. Утверждение «preview и gross сверены у обоих брокеров по значению» не соответствует коду.

13. **[P2 — ЛОЖНОЕ WORM-доказательство] `live/worm_anchor.py`, `snap`: якорь коммитится раньше публикации архива.**  
    В HEAD сначала попадает текст про финальное имя `addfut-*.tgz`, тогда как существует только `.tgz.pending`. Лишь после коммита выполняется `os.replace(...pending, ...tgz)`. SIGKILL, потеря питания или ошибка rename оставляют долговечный WORM-якорь, утверждающий наличие архива под именем, которого никогда не было. Обработчик ошибки не может отменить уже опубликованный коммит. Следующий `backup_push` способен выгрузить это ложное заверение наружу.
