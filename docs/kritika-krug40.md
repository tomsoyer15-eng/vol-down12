# Рецензия сорокового круга ред. 33 (gpt-5.6-sol, pro+max)

1. **КРИТИЧНО — целевая книга может пройти с недостаточной маржой.**  
   **Файл:** `live/ib_broker.py`  
   **Функция:** `IBBroker.preview`

   Ветка

   ```python
   if _need <= 0:
       return bool(float(_c) >= _DLp.O3E_MIN)
   ```

   выходит **до** вычисления `_pos_need`, `_cur_req` и `_worst`. Обещанная проверка худшей из трёх оценок выполняется только при положительной сумме приращений. Например, при `[-900k, +800k]` сумма отрицательна, текущий cushion здоров — переход разрешён, хотя одна положительная часть требует `$800k` и при NLV `$1m` даёт запас лишь `1.25x`.

   Это не аварийное исключение: `preview()` не получает ни направление перехода, ни `emergency`; обход действует для любого Ф→Е/Е→Ф. Старый файловый замер может быть занижен, поэтому именно свежий preview должен был остановить открытие полной неверной книги.

   **Ложное доказательство:** `IBBroker.SAME_API` этого не проверяет:
   - `StubIB.accountSummary()` вообще не возвращает `FullInitMarginReq`;
   - все проверяемые `whatIfOrder` дают положительные приращения, поэтому `_need == _pos_need`;
   - `StubIB.whatIfOrder()` не проверяет `order.account`, значит заявленная привязка preview к пинованному счёту тоже не наблюдается.

2. **КРИТИЧНО — бесплатная упаковка ролла всё ещё превращается в фиктивный расход и лишний cap-срез.**  
   **Файл:** `live/daily.py`  
   **Функции:** `repack_excess`, `step`

   Исправлен только ролл с неизменным `n_e`. При изменении количества через границу упаковки код снова считает канонизацию избытком. Пример:

   - до ролла: `n_e=19`, канон `1 ES + 9 MES`;
   - после ролла: `n_e=20`, канон `2 ES`;
   - `repack_excess()` приводит серии к общей и получает оборот `+1 ES -9 MES` = 19 единиц сетки при чистом изменении 1;
   - возвращает фиктивный excess 18.

   Но при полном ролле старая упаковка всё равно закрывается, а новая открывается целиком; эти 18 единиц не являются дополнительным оборотом по принятой норме. `step()` вычитает их из `_e_gate` и у границы 2,00 продаёт лишний контракт — фактическая позиция становится ниже нормативной.

   **Ложные доказательства:**
   - `live/invariants.py::_i12a` прямо требует `d.book_after.n_e == b.n_e`, исключая опасный ролл с изменением количества;
   - `_i12b` канонизирует только при `m.roll_today`, но не при `roll_pending` и навёрстывании;
   - в `live/mutation.py::run_pack_mutations` подмены `repack_excess` принимают три аргумента, тогда как `step()` вызывает её с четвёртым `roll_a`. Мутация «ловится» через `TypeError`, а не проверкой cap-смысла.

3. **ВЫСОКИЙ — штатная ротация backup гарантированно остановит контур и доведёт фьючерсы до поставочной зоны.**  
   **Файлы:** `live/worm_anchor.py`, `live/autopilot.sh`  
   **Функции:** `anchors_without_archive`, `snap`, `backup_state`

   `backup_state()` оставляет только 60 архивов:

   ```bash
   tail -n +61 | xargs -r rm -f
   ```

   При этом WORM-якоря не удаляются. `anchors_without_archive()` требует локального наличия архива для **каждого** нового якоря. После создания 61-го архива уборка штатно удалит самый старый; следующий `snap()` объявит его «отсутствующим заверенным архивом» и будет отказывать бесконечно.

   Замыкание книги к этому моменту уже выполнено, но `closed-*` не ставится, возникает ALARM, следующие торговые сессии и ролл запрещаются. Это детерминированный отказ примерно после 62 снимков, а не аварийный край.

   Дополнительно проверка смотрит только рабочее дерево `ROOT/anchors`, а не заверенные blobs Git: удалённый локально, но существующий в WORM-истории якорь станет невидимым.

   **Ложное доказательство:** среди `RUN_CASES` нет сценария «якорь есть, архив удалён штатной retention-уборкой». Успешный WORM-стенд запускается в свежем репозитории без старого якоря, то есть опасная ветка не достигается.

4. **ВЫСОКИЙ — чужой `TRANSITION_OPEN` проверяется после мутации прогресса и вообще обходится при отказе preview.**  
   **Файл:** `transition.py`  
   **Функция:** `_execute_locked`

   `open_tid` уже известен из первого `derive_state()`, но проверка чужого tid стоит только после:

   - создания нового `state_path`;
   - записи snapshot/digest;
   - вызова preview;
   - изменения и записи `postponed`.

   Если preview вернул `False`, первые два запуска возвращают `POSTPONED` **до проверки чужого OPEN**. На третьем отказе вызываются `hook('open')` и `hook('abort')`, но их булевы результаты игнорируются. Таким образом, обещанного «О-5 до создания чего-либо» нет даже по управлению потоком.

   Денежного ордера пока нет, но прогресс нового перехода уже создан поверх неразобранной эпохи. После разрешения чужого OPEN этот файл способен блокировать законный переход несовпавшим `tid` либо быть ошибочно принят как начало собственного сценария.

   **Ложное доказательство:** foreign-OPEN стенд использует только успешный preview и проверяет лишь отсутствие broker calls и сохранность чужой метки. Он не проверяет, что `state_path` не появился и не изменился; фактически стенд закрепляет эту мутацию как допустимую.

5. **ВЫСОКИЙ — сообщения чистого отказа О-3-Е лгут о уже состоявшихся заявках и о книге брокера.**  
   **Файлы:** `live/daily.py`, `live/session.py`  
   **Функции:** `run_session`, `do_o3e_cut`

   В пост-трейдовом срезе при закрытии окна до первой заявки среза выдаётся:

   ```text
   ни одной заявки этим запуском не подано
   ```

   Но этот же запуск уже мог исполнить основной ребаланс, сохранить `_mid` и только затем дойти до среза. Правдивое утверждение — «не подано ни одной заявки **среза**».

   В отдельном `do_o3e_cut()` сообщение ещё сильнее:

   ```text
   книга не тронута
   ```

   Доказано только отсутствие заявки данного вызова. Поздний fill или ручная сделка после последнего снимка не исключены.

   **Ложное доказательство:** `live/invariants.py::_r_edge` одновременно требует `placed == 2` и принимает ошибку с текстом `НЕ НАЧАТО`; то есть стенд знает, что две заявки этого запуска уже поданы, но не отвергает сообщение «ни одной заявки этим запуском». Противоречие закреплено зелёным тестом.

6. **ЛОЖНОЕ ДОКАЗАТЕЛЬСТВО — стенд «свой чистый отказ открытия снимает метки» не достигает `_mark_handover` и `hook('open')`.**  
   **Файл:** `selfcheck_v192.py`  
   **Блок:** проверка `СВОЙ чистый отказ открытия не оставляет меток...`  
   **Связанная функция:** `_sig`

   Стенд делает `_sig('F')`. Эта фикстура сначала завершает переход в Е, поэтому действующий маршрут журнала становится `E`, затем создаёт pending в `F`. После этого вызывается `T.execute()` с параметрами по умолчанию `from_route='F', to_route='E'`.

   Запуск падает раньше проверяемой ветки:

   ```text
   from_route=F не совпадает с маршрутом журнала E
   ```

   Ни `_mark_handover`, ни отказ `hook('open')`, ни `_drop_handover` не исполняются. Утверждение проверяет только то, что уже отсутствующие метки остались отсутствующими. Это ровно недостижимый зелёный зонд.
