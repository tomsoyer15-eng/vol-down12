# Рецензия тридцать восьмого круга ред. 33 (gpt-5.6-sol, pro+max)

1. **Критический — рассинхронизация с брокером: штатный `resume` частично исполненного перехода недостижим.**  
   **Файлы:** `transition.py`, `_execute_locked()`, `_preflight_handover()`; ложный стенд — `selfcheck_v192.py`, `_B.__init__()`, `_seed_books_from()`.  
   `_preflight_handover()` безусловно сверяет текущие позиции брокера с исходной книгой маршрута. После хотя бы одного исполненного лота это расхождение является нормальным состоянием перехода: книга на диске ещё исходная, брокер уже промежуточный. Поэтому `resume=True` отвергается до кода восстановления:
   ```python
   _preflight_handover(..., _broker_p=broker)
   ```
   Штатно продолжить частичный переход нельзя; остаётся непарная позиция и ручной разбор. Стенд скрывает дефект: каждый новый `_B` вызывает `_seed_books_from(s.np)` и переписывает исходную книгу по уже промежуточным позициям брокера — делает в фикстуре ровно ту мутацию состояния, которой в бою не происходит.

2. **Критический — чистый отказ окна всё ещё запускает торговое `restore_to()`.**  
   **Файл:** `live/daily.py`, `run_session()`, обычный цикл заявок и пост-трейдовый срез О-3-Е.  
   Исправлена только `execute_roll()`. В обычном пути `WindowClosed` попадает в общий `except Exception`, хотя `broker.place()` ещё не вызывался:
   ```python
   try:
       _window_gate(...)
       rec = broker.place(...)
   except Exception:
       restore_to(...)
   ```
   То же осталось в цикле `_cut_orders` О-3-Е. Если между последней сверкой и воротами пришёл поздний fill или ручная сделка, `restore_to()` автоматически компенсирует её уже за краем окна, хотя текущий запуск не подал ни одной заявки.  
   На пути О-3-Е есть второй ущерб: при чистом отказе первого среза намерение не очищается. Книга сохранена как `_mid`, но `do_close()` теперь отвергает незавершённое intent — фактическое закрытие и триггер капа блокируются до ручной хирургии. `session.do_o3e_cut()` этот случай различает, `daily.run_session()` — нет.

3. **Ложный стенд края окна не достигает проверяемого среза.**  
   **Файл:** `live/invariants.py`, `_session_run()`, случай `Е: срез у самого края окна`.  
   Стенд ставит часы на 09:35 при крае Е 09:45. Его перехватывает начальная проверка `run_session(... margin_min=True)` ещё до основной сделки. Пост-трейдовый срез О-3-Е и его первые ворота не исполняются вообще. Кроме того, ни один `@rinv` не имеет `needs` для этого случая. Сценарий присутствует в списке, но не содержит утверждения и закрепляет ничего.

4. **Высокий — `preview()` не доказывает маржу целевой книги и может разрешить неверную позицию.**  
   **Файл:** `live/ib_broker.py`, `IBBroker.preview()`.  
   Сразу три дефекта:
   - `MarketOrder` для `whatIfOrder` не получает `order.account = self.account`; результат не привязан к пинованному торговому счёту.
   - Каждый target-order просматривается отдельно против всё ещё существующей исходной книги. Затем складываются `initMarginChange`, как будто это полная маржа целевого портфеля. Нелинейные offsets с исходными активами исчезнут после их продажи, но могут занизить `_need`.
   - Отрицательная суммарная `initMarginChange` объявляется безопасной:
     ```python
     if _need <= 0:
         return True
     ```
     Это не доказательство нулевой маржи цели.
   
   Именно при изменившемся house-margin, ради которого добавлен живой preview, старый файловый предполёт может пропустить цель, а эта проверка даст ложное разрешение по другому счёту или по временно хеджированной смешанной книге.

5. **Высокий — успешный Е→Ф часто блокируется дробной what-if заявкой на фьючерс.**  
   **Файл:** `transition.py`, `_execute_locked()`; `live/ib_broker.py`, `preview()`.  
   `_pv_orders` строится сырым отношением:
   ```python
   units * unit_usd / dprice
   ```
   без того округления, которым реально торгует `_run_lots()` и которым строится `target_book()`. Для цели FUT получается, например, `109.295 MES`. Такая what-if заявка на фьючерс недопустима у IBKR и даст пустой/ошибочный ответ; после трёх попыток законный переход уйдёт в ABORT.  
   `ib_stub.whatIfOrder()` принимает дробный FUT и потому не воспроизводит биржевую границу.

6. **Высокий — кап `gross` считается не по заявленной живой доходности и допускает NaN.**  
   **Файлы:** `live/ib_broker.py`, `IBBroker.gross()`; `transition.py`, `_gross_dfix()`, `_run_lots()`, `_execute_locked()`.  
   - `gross()` зовёт `feed.yield_pct()`, а та возвращает закрытие предыдущей сессии. Сегодняшний незавершённый бар намеренно отбрасывается. Утверждение «по живой доходности» ложно; при `CLOSE_CAP=2.00` даже небольшой внутридневной сдвиг может превратить прошедшие 1.999x в фактические >2x.
   - `_gross_dfix()` без проверки даты предпочитает процесс-глобальный `_PREFLIGHT_DFIX`. После прежней неудачной Е→Ф попытки следующий Ф→Е в том же процессе может считать ZN по старому `d_fix`, игнорируя действующую книгу Ф.
   - Ни `gross()`, ни вызывающие ворота не требуют конечного результата. При `q=NaN` получается `g=NaN`, а обе проверки
     ```python
     if g > INTRA_CAP
     if g > CLOSE_CAP
     ```
     ложны. Переход может дойти до `COMPLETE` с непроверенным плечом.

7. **Ложное доказательство — `SAME_API` не вызывает методы, ради которых объявлен исправленным.**  
   **Файл:** `live/ib_broker.py`, `SAME_API()`.  
   Вопреки комментарию:
   - `preview()` не вызывается ни у живого адаптера, ни у макета;
   - `gross()` не вызывается ни у одного;
   - `unit_ref()` вызывается только у живого адаптера, не у макета;
   - дробность проверяется на `rows[0]`, то есть `ESU26`, а не на `CSPX/CBU0`.
   
   Поэтому `ib_stub.whatIfOrder()` фактически мёртв для этой проверки, а регрессии к старому preview и середине полосы ZN останутся зелёными. Отдельных мутаций `preview`/`gross` также нет.

8. **Высокий — новая семантика «OPEN уже записан» покрывает только одну точку вызова.**  
   **Файлы:** `transition.py`, `_execute_locked()`, `fail()`; `mr_engine.py`, `_append_raw()`, `confirm_transition()`.  
   Обработан только основной `hook('open')`. Остались:
   - ветка третьего отказа preview:
     ```python
     hook('open')
     hook('abort')
     ```
     Она находится вне обработки `StateCacheFailed`. Если OPEN записан, а кэш отказал, наружу выходит исключение; handover-меток здесь ещё нет, ABORT и ALARM не гарантированы.
   - `fail()` так же не различает `StateCacheFailed` после уже записанного ABORT.
   - `_append_raw()` сначала fsync-ит событие журнала, затем вызывает `_stamp_journal_digest()`. Отказ записи deploy-digest после fsync оставляет долговечный OPEN, но исключение не имеет `committed=True`. Основной обработчик считает это чистым отказом и снимает метки.
   
   В результате нормативный журнал может держать OPEN, а единственный файловый барьер ежедневного контура отсутствовать. Стенд `_wsc_fail` проверяет только `not open_tid` на основном пути; он не проверяет ветку preview, тип терминального события, handover-метки и ALARM.

9. **Средний — `autopilot.STOP` перечитывается не перед последней мутацией тика.**  
   **Файл:** `live/autopilot.sh`, `tick()`.  
   Повторная проверка STOP добавлена после `run_trade`, но вахта О-3-Е идёт позже и сама может создать STOP: при отказе тревоги, счётчика либо внутреннего `session.py --o3e`. После неё код без новой проверки выполняет:
   ```bash
   ensure_gw && run_close "$day"
   ```
   Для маршрута Е это реальный путь после 10:35. То есть STOP, который по заявленной политике запрещает и замыкание, не мешает тому же процессу финализировать книгу, backup и WORM.

10. **Средний — stderr всё ещё навсегда глушится другим `exec`.**  
    **Файл:** `live/autopilot.sh`, `ensure_gw()`.  
    Исправлена строка открытия fd 9, но остались:
    ```bash
    if exec 3<>/dev/tcp/127.0.0.1/4002 2>/dev/null; then
    ```
    и такой же вызов в цикле. `exec` без команды применяет `2>/dev/null` к текущей оболочке навсегда. На каждом здоровом вызове `ensure_gw` весь последующий stderr тика снова исчезает. Неожиданный bash-сбой, arithmetic error или `command not found` после проверки порта не даст cron-письма — ровно тот дефект, который комментарий объявляет устранённым.

11. **Средний — `_alarm_o3e()` ложно утверждает, что STOP поставлен.**  
    **Файл:** `live/session.py`, `_alarm_o3e()`.  
    Основной ALARM fsync-ится, но аварийный STOP пишется так:
    ```python
    try:
        (... / 'autopilot.STOP').write_text(...)
    except Exception:
        pass
    raise Refused('... поставлен STOP')
    ```
    Нет fsync файла и каталога, нет проверки существования/размера, а полный отказ записи проглатывается. При ENOSPC/ACL наружу всё равно уходит утверждение «STOP поставлен». Если и shell-`alarm_write` не сможет создать барьер, следующий cron снова войдёт в торговый путь при незавершённом intent или уже исполненном срезе.
