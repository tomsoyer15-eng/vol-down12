# Рецензия восьмого круга ред. 33 (gpt-5.6-sol, pro)

## Критические дефекты

### 1. После смены маршрута стирается временная история книги — разрешена повторная торговля в ту же сессию

**Файлы:** `transition.py::hand_over_book`, `live/state.py::book_from_broker`, `live/session.py::do_trade`

`hand_over_book()` сохраняет новую книгу так:

```python
_ST2.save(_ST2.book_path(to_route), _bk, to_route, 0, ...)
```

`book_from_broker()` не переносит `last_session`, `prev_close_lev` и состояние замыкания. Получается книга с:

- `session_no = 0`;
- `last_session = None`;
- `close_provisional = True`;
- потерянным фактическим плечом закрытия.

После этого защита в `do_trade()` не работает:

```python
if sess and getattr(book, 'close_provisional', False) and not dry:
```

При `sess == 0` условие ложно. `run_session()` тоже не остановит повтор, поскольку `last_session=None`.

**Денежный исход:** сразу после перехода можно второй раз в тот же день пересчитать и перестроить уже переведённую книгу. На новом маршруте `prev_st_*` часто `None`, поэтому обе ноги считаются переключившимися и могут получить дополнительные заявки.

**Ложное доказательство:** `live/invariants.py::_session_route_switch` запускает торговлю Е только **на следующий день**. Опасный сценарий «переход и ежедневная торговля в одну дату» отсутствует.

**Требование:** передача обязана сохранять дату операционной сессии и запрещать ежедневный запуск в эту дату; номер сессии нельзя обнулять. Переход должен завершаться предварительно замкнутой книгой с явным `last_session=asof`.

---

### 2. Признак `roll_pending` на самом деле не переживает переход Ф→Е

**Файлы:** `transition.py::hand_over_book`, `live/state.py::book_from_broker`, `live/daily.py::BookE`

`hand_over_book()` передаёт:

```python
_ST2.book_from_broker(..., roll_pending=_prev_pending)
```

Но ветка маршрута Е этот аргумент выбрасывает:

```python
if route == 'E':
    return cls(n_eq=..., n_bd=..., prev_st_eq=..., prev_st_bd=...)
```

У `BookE` поля `roll_pending` вообще нет. Дополнительно любая ошибка чтения исходной книги молча превращается в отсутствие отложенного ролла:

```python
except Exception:
    _prev_pending = False
```

**Денежный исход:** незавершённая операция исчезает из состояния при смене маршрута. При последующем возвращении в Ф система не знает, что перенос серии не был завершён.

**Ложное доказательство:** сценарий `live/invariants.py::_roll_seq`, названный «переход посреди отложенного ролла», маршрута не меняет. Он вызывает:

```python
ST.book_from_broker(DL.Book, ..., 'F', roll_pending=...)
```

То есть проверяет реконструкцию **Ф→Ф**, а не `transition.hand_over_book()` и не Ф→Е→Ф. Стенд проверяет собственную упрощённую симуляцию.

**Требование:** операционный pending должен храниться в маршрутно-независимом состоянии перехода либо в обеих книгах. Ошибка чтения исходной книги должна останавливать передачу, а не приравниваться к `False`.

### 3. Сборщик принимает закрытие позапрошлой сессии как вчерашнее

**Файл:** `live/feed.py::closes`

Проверяется только календарный возраст:

```python
gap = (t - d_prev).days
if gap > MAX_BAR_GAP_D: ...
```

`MAX_BAR_GAP_D = 5`. Во вторник устаревший пятничный бар имеет возраст четыре дня и проходит. Если ES и TNX одинаково отстали, межисточниковая сверка также проходит.

**Денежный исход:** цель обеих ног считается по старому закрытию, хотя понедельничная сессия уже завершилась. Возможны неверный размер позиции, пропуск полосы и ошибочная кап-коррекция.

**Ложное доказательство:** случаи `_feed_run('бар вчерашний повторён')` и `'ОБА источника устарели одинаково'` подсовывают бары недельной давности. Случай «пропущена ровно одна обычная сессия, но возраст ≤5 дней» не проверяется.

**Требование:** дата бара должна совпадать с последней завершённой сессией соответствующего официального календаря, а не просто укладываться в пятидневный допуск.

---

### 4. Восстановление может снять заявки другого счёта или другой стратегии

**Файлы:** `live/ib_broker.py::open_orders`, `live/ib_broker.py::cancel_order`, `live/daily.py::_cancel_all`

Позиции фильтруются по счёту, заявки — нет:

```python
return sorted({t.order.orderId for t in self.ib.openTrades()})
```

`_cancel_all()` снимает всё, что вернул `open_orders()`. Не проверяются:

- `order.account`;
- принадлежность стратегии;
- `clientId`;
- `permId`;
- инструмент текущего намерения.

Комментарий прямо объявляет, что это «живые заявки всего счёта». Для multi-account это ещё хуже: `reqAllOpenOrders()` может открыть видимость заявок иных управляемых счетов.

**Денежный исход:** авария ADD-FUT отменяет ручную защитную заявку, заявку другой стратегии или заявку соседнего managed account.

**Ложное доказательство:** сценарий `other_account` в `live/invariants.py::_a9` проверяет только фильтрацию **позиций**. Чужих открытых заявок стенд не создаёт.

**Требование:** отменять можно только заявки точного счёта и текущего намерения. Остальные заявки должны блокировать сессию, но не сниматься автоматически.

### 5. Отложенный ролл не списывает ролловую стоимость и завышает капитал

**Файл:** `live/daily.py::step`

Решение признаёт отложенный ролл:

```python
roll_now = m.roll_today or b.roll_pending
```

Кап-аллокатор тоже учитывает стоимость при `roll_now`. Но окончательное списание сделано только по исходному календарному флагу:

```python
if m.roll_today:
    e -= S.ROLL_BP * (exp_e + exp_b)
```

При `b.roll_pending=True`, `m.roll_today=False` серия переносится, но `capital_after_costs` не уменьшается.

**Денежный исход:** завышаются капитал и доступное плечо; пограничная книга может получить на один контракт больше. Журнал и последующая сверка издержек также расходятся с фактическим переносом.

**Ложное доказательство:** `_roll_seq` проверяет только серии и `pending`; капитал, leverage и ролловое списание не проверяются.

**Исправление:** во всех расчётах использовать один признак `roll_now`, включая окончательное списание и причину сделки.

### 6. Ролл плюс изменение экспозиции целиком выдаётся за ролловый оборот

**Файл:** `live/journal.py::rows_from_decision`, `live/journal.py::reconcile`

Код пытается разделить входящую заявку на ролловую и обычную части. Но обе строки получают общий `reason`:

```python
reason='; '.join(dec.reasons)
```

В день ролла там есть `ролл серии`. Затем классификация выполняется так:

```python
is_roll = lambda r: 'ролл' in (r['reason'] + r['note'])
```

Поэтому даже строка обычного остатка с пустым `note` снова классифицируется как ролл из-за `reason`.

**Денежный исход:** обычный оборот по модели 5 б.п. попадает в выборку ролла 1 б.п. Результат §7 систематически искажён именно в сессиях «ролл + сигнал», «ролл + полоса» и «ролл + кап».

**Ложное доказательство:** `live/contour_test.py` создаёт отдельные синтетические строки с `reason='ролл серии'`. Реальный путь `rows_from_decision()` для смешанной сессии не проходит.

**Требование:** тип стоимости должен быть отдельным структурным полем строки (`cost_class=trade|roll`), а не выводиться поиском слова в свободном тексте.

## Потеря синхронизации и порча состояния

### 7. «Гонка при замыкании» не воспроизводит реальную гонку

**Файл:** `live/invariants.py::_session_race`

`do_close()` держит `ST.hold_book_lock()` всё время. Настоящий `transition.execute()` берёт тот же замок и в окно войти не может.

Стенд же подменяет `FD.closing_values` и внутри него напрямую вызывает `ST.save()` без захвата замка:

```python
ST.save(bp, replace(b, n_b=b.n_b + 7), ...)
```

Это не конкурентный переход, а намеренное нарушение протокола блокировки внутри того же процесса.

**Ложное доказательство:** PASS доказывает только, что второе чтение замечает безусловную запись кода, который проигнорировал замок. Он не доказывает общность замков между реальным `session.py` и `transition.py`, разные `HOME`, разные `ADDFUT_LOCK_DIR` и разные процессы.

**Требование:** тест должен запускать реальный `transition.hand_over_book`/`execute` в отдельном процессе и доказывать, что он блокируется до конца `do_close`.

---

### 8. `run_session()` блокирует не переданный `book_path`, а глобальный машинный каталог

**Файлы:** `live/daily.py::run_session`, `live/state.py::hold_book_lock`

`run_session()` получает `dirpath` и `book_path`, но делает:

```python
with ST.hold_book_lock():
```

`dirpath` игнорируется. `hold_book_lock()` также фактически игнорирует свой `dirpath`, потому что `lock_dir(hint)` не использует `hint`.

**Денежный исход:** явно переданная книга может защищаться замком, не связанным с её расположением. Два запуска с разными окружениями могут работать по одному файлу под разными lock-файлами либо по разным счетам под одним lock-файлом.

`live/contour_test.py` при самостоятельном запуске также пишет lock-файл в настоящем `~/.addfut`, несмотря на временный `book_path`.

**Требование:** идентификатор замка должен быть привязан к account+strategy и передаваться явно, без сочетания аргумента книги с неявным окружением.

---

### 9. Хэш состояния не защищает от подделки состояния

**Файл:** `live/state.py::_digest`, `save`, `load`

Хэш полностью некриптографичен в смысле аутентичности: это обычный SHA-256 от открытого JSON. Любой процесс с правом записи может изменить позицию, маршрут или номер сессии и пересчитать digest.

Тест в `live/contour_test.py` меняет поле, но специально не пересчитывает хэш. Он доказывает защиту от случайной порчи, а не от подмены.

**Требование:** либо HMAC с ключом вне каталога состояния, либо подпись/внешний append-only якорь. Документация не должна называть такой digest защитой от подмены.

---

### 10. Проверка личности ETF не проверяет личность ETF

**Файлы:** `live/contracts.py::mismatches`, `live/first_connect.py::main`

Для ETF реестр хранит пустые `expiry` и `multiplier`. Проверяются фактически только:

- валюта;
- `localSymbol`.

Не проверяются:

- `secType`;
- ISIN, хотя он указан только в комментарии;
- primary exchange;
- торговая биржа;
- символ;
- класс ноги.

`first_connect.py` знает ISIN, но в CSV его не записывает.

**Денежный исход:** ошибочный `con_id` другой листинговой линии с тем же локальным тикером и валютой может пройти проверку и направить приказ не в тот фонд/на не ту площадку.

**Требование:** хранить и сверять `secType`, ISIN, symbol, primaryExchange и разрешённую биржу.

## Самопроверка и стенды дают ложные доказательства

### 11. Снимок `~/.addfut` не видит точный путь, который самопроверка реально портит

**Файлы:** `selfcheck_v192.py::_machine_snapshot`, `live/tz.py::install`

Снимок обходит только верхний уровень:

```python
for _fn in os.listdir(_REAL_ADDFUT):
    if os.path.isfile(_fp):
        out[_fn] = sha256(...)
```

Но `live/tz.py` при импорте пишет сюда:

```python
~/.addfut/zoneinfo/US/Central
~/.addfut/zoneinfo/...
```

`ADDFUT_LOCK_DIR` на `tz.DIR` не влияет. Подкаталог `zoneinfo` снимок полностью игнорирует. Подпроцессы `invariants.py` импортируют `tz`, поэтому самопроверка способна создать или изменить машинный каталог и всё равно напечатать:

> стенды не тронули машинное состояние ~/.addfut

Это уже готовое ложное доказательство, а не теоретическая возможность.

---

### 12. Снимок не видит права, владельца, симлинки, каталоги и запись с откатом

**Файл:** `selfcheck_v192.py::_machine_snapshot`

Не фиксируются:

- тип объекта;
- цель symlink;
- mode/ACL;
- uid/gid;
- каталоги и их содержимое;
- xattr;
- mtime/ctime;
- удаление и восстановление между двумя снимками.

`os.path.isfile()` следует по symlink. Поэтому обычный файл можно заменить симлинком на объект с тем же содержимым — хэш останется тем же. `chmod 000` также невидим. Запись вредных данных с последующим откатом перед финальным снимком невидима по построению.

Кроме того, первый снимок делается не в самом начале процесса: до него уже импортированы модули и вызван `M.set_state_dir_for_tests()`.

**Требование:** самопроверка должна запускаться в mount/user namespace с отдельным `HOME`, а не пытаться доказать невмешательство двумя снимками. Финальный аудит должен рекурсивно использовать `lstat`, фиксировать типы, ссылки, права и владельцев.

---

### 13. Монки-патчи могут протечь между сценариями при ошибке подготовки

**Файл:** `live/invariants.py::_session_run`

Патчи устанавливаются до входа в защищённый `try/finally`:

```python
ib_insync.Index = Idx
FD.registry = lambda: ...
FD.signal_state = lambda ...
...
ST.save(bp, b0, route, 1)   # ещё до try
...
try:
    ...
finally:
    # восстановление
```

Если `ST.save`, построение книги или иной setup-код под мутацией падает, `finally` не выполняется. Следующие сценарии идут с чужими `Index`, `registry`, `signal_state` и окружением.

`run_run()` ловит исключение стенда и продолжает, поэтому отравление может распространиться на остальные случаи.

**Требование:** патчи должны устанавливаться context manager’ом, охватывающим весь setup, либо каждый сценарий должен выполняться в отдельном процессе.

---

### 14. Мутационная проверка может объявить все мутации пойманными из-за одного старого baseline-отказа

**Файл:** `live/mutation.py`

Для основного перебора baseline вычитается:

```python
fired = run_once() - base
```

Но для адаптера, feed, запуска, перехода и ролла baseline вообще не вычитается. Например:

```python
_, bad = I.run_feed()
if bad:
    # мутация считается пойманной
```

Если исходный тест уже падает из-за переформулировки сообщения — например, больше не содержит `'отстал'` или `'множитель'` — этот же baseline-отказ будет присутствовать при каждой мутации. Таблица напечатает «да, поймана» для всех мутаций независимо от их эффекта.

Отдельно `base` в основном прогоне лишь печатается как предупреждение и не включён в итоговый код возврата:

```python
if base:
    print('ВНИМАНИЕ...')
...
sys.exit(1 if (missed or miss_a) else 0)
```

**Это и есть путь, где изменение текста сообщения выключает доказательную силу мутаций.**

**Требование:** сначала обязательный чистый baseline с нулём отказов; затем для каждой мутации учитывать только новые отказы относительно baseline и проверять ожидаемого «убийцу», а не любое `bad`.

### 15. Проверки по подстрокам засчитывают постороннее исключение как нужную защиту

**Файлы и функции:**

- `live/invariants.py::_f3` — `'отстал'`;
- `live/invariants.py::_f9` — `'множитель'`;
- `live/invariants.py::_r4` — `'не замкнута'`;
- `live/invariants.py::_s2b` — `'О-5'`, `'ручной разбор'`;
- `live/invariants.py::_s2c` — `'заяв'`;
- `live/contour_test.py`, проверка частичного исполнения — набор очень широких слов.

Это проверка литературной формулировки, а не причины отказа. Любая другая ошибка с подходящим словом даёт PASS; корректный структурный отказ с новым текстом даёт FAIL и, согласно предыдущему замечанию, способен превратиться в ложного «убийцу» всех мутаций.

**Требование:** типизированные исключения и машинные коды причин: `STALE_BAR`, `MODEL_MULT_MISMATCH`, `OPEN_ORDER_PRESENT`, `BOOK_DIVERGED`, `CLOSE_PROVISIONAL`.

### 16. Эквивалентность «до 1e-12» не покрывает живой путь и частично круговая

**Файл:** `live/replay_check.py::replay`, `positions_of_sim`

Обе стороны используют общие:

- `sim_v13` и его константы;
- тот же ряд сигналов;
- `S.roll_days_calendar`;
- общие формулы стоимости и дюрации;
- заранее подготовленные входы.

Не исполняются:

- `feed.build_market`;
- праздничный календарь живого ролла;
- реестр и контрактная идентичность;
- `IBBroker`;
- физическая последовательность заявок;
- частичные исполнения;
- состояние и намерение;
- замыкание отдельным запуском.

Поэтому совпадение 1e-12 доказывает лишь согласованность двух арифметических реализаций на общих входах. Оно ничего не доказывает о главных денежных границах, хотя вывод называется «ЭКВИВАЛЕНТНОСТЬ ДОКАЗАНА».

## Журнал: пересборка цепочки — сейчас это дыра

### 17. Цепочка §7 обнаруживает только неумелую правку

**Файл:** `live/journal.py::_digest`, `verify`

В документации это частично признано: злоумышленник может изменить строки и пересчитать все последующие хэши. Никакого секрета, подписи или внешнего якоря нет. Значит тот же скрипт, которым «починили» живую цепочку, является штатным инструментом незаметной переписи истории.

Тест меняет старую строку без пересчёта хвоста и объявляет правку обнаруживаемой. Это ложное доказательство против угрозы с правом записи.

### Обязательное требование к ремонту

Пересборка допустима только как миграция, если одновременно выполнено всё:

1. исходный файл сохраняется неизменяемым;
2. вычисляется и публикуется его внешний SHA-256;
3. есть подписанное разрешение с причиной, диапазоном строк и идентификатором оператора;
4. новый genesis содержит хэш исходного файла и идентификатор миграции;
5. конечные хэши периодически якорятся вне машины — WORM/object-lock, подписанный реестр или независимый журнал;
6. торговый процесс не имеет прав переписывать старые строки;
7. утилита ремонта недоступна под учётной записью торгового процесса;
8. `reconcile()` отказывается использовать журнал без проверенного внешнего якоря после последней миграции.

Без этого «цепочка цела» означает только «файл самосогласован сейчас».

## Непокрытые денежные сочетания

### 18. Пространство состояний всё ещё пропускает требуемые комбинации

**Файлы:** `live/invariants.py::states`, `run_sessions`, `RUN_CASES`

Не перебираются по существу:

- несколько заявок одной сессии, где первая исполнена полностью, вторая частично;
- ролл и переход маршрута в один день;
- смена сигнала в день ролла через настоящий `rows_from_decision`;
- переход и ежедневная торговля в ту же дату;
- отрицательный NLV на границе `do_close`/перехода;
- счёт без USD NLV или с base currency, отличной от USD;
- чужая открытая заявка другого managed account;
- Ф→Е→Ф с сохранением `roll_pending`;
- частичное исполнение компенсационной заявки восстановления;
- позднее исполнение после принятого намерения, но до следующего снимка позиций.

Особенно показательно, что «несколько заявок с частичным исполнением» моделируется брокером с единым `behaviour`: при `partial` частичными становятся все заявки сразу. Сценария «первая изменила книгу, вторая дала partial» нет.
