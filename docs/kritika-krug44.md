# Рецензия сорок четвёртого круга ред. 33 (gpt-5.6-sol, pro+max)

## Критические дефекты

1. **[P0 — неверная позиция] `live/ib_broker.py::IBBroker.unit_ref`, `IBBroker.gross` — нога А считается по ES, а не по SPY.**  
   Код берёт закрытие `ES*`, делает `es_to_unit(ES)=ES/10` и получает:
   ```python
   u = ES_MULT * ES / 10
   ```
   Нормативная единица — `500 × SPY`. Независимого SPY здесь вообще нет. При отрицательном базисе gross занижается; книга с фактическим плечом выше 2,00 проходит `CLOSE_CAP`. Запаса между 2,00 и ошибкой до 2% нет.

2. **[P0 — неверная позиция] `live/ib_broker.py::IBBroker.preview` — «все приращения маржи неположительны» ложно объявлено доказательством разгрузки.**  
   Каждый `whatIfOrder` считается при всё ещё существующей исходной книге. Отрицательное приращение может возникнуть из-за хеджа/offset с активами, которые переход затем продаст. После продажи offset исчезнет, а целевая книга потребует положительную маржу.  
   Ветка:
   ```python
   if _ims and all(x <= 0 for x in _ims):
       return True
   ```
   особенно опасна при cushion ниже 1,0: именно там она обходит последнюю живую проверку и полагается на файловый замер до 35 дней.

3. **[P0 — поставка и неверная позиция] `transition.py::_preflight_handover`, `hand_over_book` — серия цели перехода не сверяется с календарём ролла.**  
   Проверяется, что `ZNU26` действительно U26, но не проверяется, что U26 уже уходящая. На 26.08 реестр законно содержит и U26, и Z26; переход Е→Ф может купить U26, после чего `hand_over_book` ставит `last_session=26.08`. Ежедневный `leg_target_roll()` уже не исполняется в этот день. Исправление «первый вход в день ролла открывает свежую серию» действует только в `daily.step`, но обходится переходом.

4. **[P0 — рассинхронизация] `transition.py::_execute_locked` — resume предпросматривает полный план, а не остаток.**  
   `_pv_orders` строится из всех лотов до разбора фактического прогресса:
   ```python
   for _lt in plan:
       _pv_orders[...] += ...
   ```
   При частично исполненном переходе целевая позиция уже есть, но `whatIf` спрашивает покупку полной цели поверх неё. Законный resume выглядит как книга 150–200% цели, получает `POSTPONED`, а после третьего отказа — `MIXED`. Разорванная книга остаётся без штатного продолжения именно из-за новой проверки.

5. **[P1 — поставка/порча состояния] `live/daily.py::run_session` — доказуемо отложенный ролл сохраняет сессию без строки `ИТОГ`.**  
   В обработчике `RollGap(provable=True)` записываются `last_session`, `roll_pending` и новый номер сессии, затем исключение уходит наружу **до** блока построения `_pending_total`. Автопилот по дате книги ставит `traded-*` и разрешает замыкание. После замыкания `worm_anchor._anchor_body` отвергает книгу: итог журнала относится к прошлой дате. Получается постоянный `ALARM-backup`, `closed-*` не ставится, следующий ролл блокируется.

6. **[P1 — порча состояния] `live/daily.py::run_session`, `_resume_intent` — коммит книги и журнала не восстанавливается после штатного обрыва.**  
   Нормальный порядок:
   ```text
   ST.save → clear_intent → J.append(ИТОГ)
   ```
   Смерть после `ST.save` оставляет сегодняшнюю книгу без итога. Если intent ещё есть, `_resume_intent` видит совпавшие позиции, архивирует intent и затем получает штатное «не новее». Если intent уже снят, `do_trade` сразу выдаёт тот же штатный повтор. Ни один путь не дописывает доказуемо недостающий итог и не ставит тревогу немедленно. Проблема обнаруживается только позднее WORM-замыканием, когда контур уже объявил день отторгованным.

7. **[P1 — порча состояния после перехода] `transition.py::hand_over_book` — при возврате в ранее использованный маршрут текущая сессия не попадает в журнал.**  
   Итог перехода добавляется только при пустом журнале:
   ```python
   if not _rows2:
       J.append(...)
   ```
   При Е→Ф `journal-F.csv` почти наверняка уже непуст. Новая книга получает сегодняшнюю дату и новый номер, но последняя строка журнала остаётся от старой эпохи Ф. После `--close` WORM детерминированно отказывает из-за несовпадения даты книги и итога. Выпускной round-trip это не видит, потому что после возврата не выполняет замыкание и WORM.

8. **[P1 — рассинхронизация после необратимого шага] `live/ib_broker.py::IBBroker.unit_ref` — календарь CME навязан фондам.**  
   `_prev` всегда вычисляется через `daily.holidays_for`, затем используется и для CSPX/CBU0:
   ```python
   _prev = prev_session(today, holidays=HOLIDAYS_CME)
   closes(... expected_prev=_prev)
   ```
   После американского праздника Европа могла торговать накануне. На первой общей сессии свежий ETF-бар новее `_prev`, поэтому `gross()` падает. Предполет с `at_close=False` проходит, первая пара уже исполняется, и только внутрипарный gross переводит переход в `MIXED`.

9. **[P1 — одновременная торговля] `live/state.py::hold_book_lock` — flock не привязан к имени после захвата.**  
   Зафиксирован только inode открытого файла. Восстановление каталога, `unlink` или атомарная замена `addfut-book.lock` создают новый inode; второй процесс успешно берёт новый замок, пока первый держит старый. Оба затем подают заявки и сохраняют одну книгу. Межпроцессный стенд проверяет лишь обычный flock и эту траекторию не воспроизводит.

10. **[P1 — непарная позиция] `live/ib_broker.py::mark_pair`, `minutes_since` — длительность измеряется изменяемыми настенными часами.**  
    Используется `time.time()`, а не `time.monotonic()`. Перевод часов назад делает возраст отрицательным и отключает 15-минутный предел. Дополнительно `mark_pair` использует `setdefault`: повторное использование ключа в том же объекте брокера наследует часы старого перехода и может дать ложный тайм-аут уже после первой пары.

11. **[P1 — непарная позиция] `transition.py::_order_gate`, `plan_orders` — «дневной лимит 390» считает только заявки текущего файла прогресса.**  
    `len(st['order_ids'])` не включает утренний ребаланс, ручные заявки, заявки другого clientId и предыдущий переход того же дня. Предстартовый расчет также начинает с нуля. Поэтому продажа источника может пройти как локальная №390, а фактическая следующая заявка счета будет №391 и будет отвергнута уже после продажи.

12. **[P2 — пропуск ролла] `live/autopilot.sh`, сторож занятого замка — старый дефект mtime остался на повреждённом содержимом.**  
    Если heartbeat пуст или нечисловой, код снова берёт `stat -c %Y`. `touch` или восстановление копии продлевают слепоту именно на траектории повреждённого файла. Цифровая метка из будущего ещё хуже: отрицательный возраст принудительно превращается в ноль и тревога не возникнет до наступления записанного времени. То же относится к `lock-nohb`.

13. **[P2 — ложная резервная копия] `live/worm_anchor.py::_anchor_body`, `_attested_paths` — обязательность исправлена не для всей семьи.**  
    Удалённый `margins_live.json` по-прежнему считается штатным отсутствием (`_must=False`), даже если на этой машине живой замер уже существовал. Не обязательны также `account.txt` и `signals_live.csv.sha256`. WORM успешно заверяет архив, после восстановления которого нельзя торговать или выполнить аварийный переход. Это та же самонегация, которая уже была исправлена для журнала МР через устойчивый признак deploy-конфигурации.

14. **[P2 — ложное объяснение брокера] `live/autopilot.sh::run_trade/run_close`, `live/ib_broker.py::preview`, `live/diagnose.py::SIGNS`.**
    - `grep -vE '^Error [0-9]+'` удаляет фактические ответы IBKR, включая сообщения класса 10349. Если после фильтра строк нет, успешный Python дополнительно превращается в `rc=1`.
    - `preview()` превращает любое исключение — ошибка контракта, счета, реестра, API — в безымянный `False`; после трёх попыток сообщение утверждает, что отвергнута маржа.
    - Текст О-3-Е «запас ниже порога» попадает под общую сигнатуру `'ниже порога'`, и диагност объявляет причиной NLV ниже порога §8 маршрута Ф. Для маржинального инцидента Е это противоположный диагноз.

## Ложные доказательства

1. **`live/ib_stub.py::margin_call` не достигается ни одним судьёй.**  
   Режим определён, но отсутствует в `ADAPTER_CASES`; аварийный тест в `SAME_API` использует `thin_cushion=1.20`, а не значение ниже 1,0. Возврат раннего запрета `if cushion < 1.0: return False` останется зелёным и снова закроет аварийный Е→Ф.

2. **TIF замера маржи не защищён вообще.**  
   `first_connect.main()` не исполняется адаптерным судьёй, а мутация TIF существует только для `IBBroker.preview`. Удаление `_o.tif='GTC'` из `first_connect.py` не уронит выпуск: генератор просто перестанет обновлять маржу, пока свежий старый файл ещё проходит возраст.

3. **Проверка gross доказывает только зависимость от `d_fix`, не масштаб.**  
   `_a14` проверяет отношение `gross(12)/gross(6)==2`. Реализация `0.5 × правильный gross` пройдет. Нога А и фонды там вообще отсутствуют. Поэтому реальный дефект ES вместо SPY остается зелёным.

4. **`_a31u` круговой:**  
   ```python
   _spy = 7747.5 / 10.0
   ```
   «Независимый SPY» выводится из того же ES, которым строится проверяемая полоса. Это не проверяет правило `500×SPY`.

5. **Смешанные приращения preview не покрыты.**  
   Стаб задаёт один режим whatIf сразу всем заявкам. Сценария `[-900k, +800k]` нет. Возврат раннего разрешения по отрицательной сумме не поймают ни «всё отрицательно», ни «всё тесно».

6. **`invariants.py::_session_run` — да, сравнение `st_mtime_ns` тревоги и книги является дырой доказательства.**  
   mtime не задаёт happens-before: значения могут совпасть, откатиться при коррекции часов или быть переписаны повторным открытием файла. «Один процесс и несколько секунд» — совпадение текущей машины, не механизм. Нужен журнал вызовов/инъецированный наблюдатель порядка, а не метаданные файлов.

## Шесть непокрытых методов IBBroker

- **`buy_units`, `sell_units` — денежно критические.** Знак, дробность и фактически возвращённый объём непосредственно определяют позицию.
- **`mark_pair`, `minutes_since` — денежно критические.** Это единственная защита продолжительности непарной дельты; текущая реализация уже содержит дефект `time.time()`.
- **`todays_executions` — денежно критический.** От него зависит ABORT против MIXED и допустимость повторной подачи.
- **`_px_hint` — вспомогательный.** Он не задаёт цену рыночной заявки; `place()` повторно получает контракт и при наличии снимка заменяет ориентир. В переходе возвращённая цена вообще отбрасывается. Мутация ради позиции здесь будет ритуалом; смысл есть только для контроля аудиторского `px_order`.
