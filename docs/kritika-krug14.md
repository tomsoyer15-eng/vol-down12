# Рецензия четырнадцатого круга ред. 33 (gpt-5.6-sol, pro)

1. **КРИТИЧНО — `live/daily.py`, `restore_to`: восстановление подаёт компенсирующие заявки при неснятой живой заявке.**  
   `_cancel_all()` возвращает `stuck`, но `restore_to()` всё равно вычисляет разницу позиций и вызывает `broker.place()`. Денежный путь: BUY 10 частично исполнился на 4, остаток 6 остался живым; восстановление продаёт 4 к исходной книге, затем остаток BUY 6 исполняется позднее. На счёте +6, файл считает исходную позицию восстановленной либо сообщает лишь общий инцидент. Строгая охрана живой заявки реализована только в тексте результата, но не до компенсирующей торговли. При `stuck` функция обязана не подавать ни одной новой заявки.

2. **КРИТИЧНО — `live/first_connect.py`, `main`: частичный замер маржи публикуется как полноценный живой файл.**  
   Защищён только случай `margins == {}`. Если what-if вернул ES, но не вернул ZN, непустой словарь атомарно затирает прежний полный `margins_live.json`. Затем `transition.py::_live_margins` считает файл исправным, а `book_margin` для отсутствующего корня молча берёт `FUT_MARGIN`. Денежный путь: фактическая house-маржа ZN повышена, её запрос сорвался, переход разрешается по старой константе и получает недостаточный запас/ликвидацию. Нужна проверка полноты всех требуемых корней и серий до публикации.

3. **КРИТИЧНО — `live/first_connect.py`, `main`: what-if маржа снимается без пинования счёта.**  
   `MarketOrder('BUY', 1)` не получает `account`, подключение допускает несколько `managedAccounts()`, а позиции для добавления удерживаемых серий также собираются со всех счетов. Денежный путь: `margins_live.json` формируется по default/чужому managed account с другими house-требованиями; переход на пинованном торговом счёте проходит ложный preflight. Пинование в `IBBroker` этого не исправляет: опасный файл уже создан другим кодом.

4. **ВЫСОКИЙ — `live/daily.py`, `step`: просрочка только ноги А незаконно перефиксирует `d_fix` ноги Б.**  
   Условие:
   ```python
   if roll_any or bd_switch:
       b = replace(b, d_fix=m.dref_prev)
   ```
   срабатывает при `missed_a=True`, даже если `roll_b=False` и ZN не роллится. Денежный путь: смешанная книга `ser_a=U26`, `ser_b=Z26`; навёрстывание только ES/MES меняет модельную единицу ZN, после чего полоса и цель Б считаются по новой дюрации и создают лишнюю либо недостаточную заявку ZN. `d_fix` должен меняться по `roll_b or bd_switch`, а не по роллу любой ноги.

5. **ВЫСОКИЙ — `live/daily.py`, `step`: навёрстываемый ролл одновременно объявляется успешно навёрстываемым и поставочно запрещённым.**  
   Для просроченной U26 в сентябре `missed_a/missed_b=True`, но `roll_now=False`. Позже проверяется старая серия:
   ```python
   if ... delivery_risk(held, m.date) and not roll_now:
       d.refusals.append(...)
   ```
   Поэтому решение строит перенос в Z26 и одновременно получает отказ «требуется ручной разбор». После фактического исполнения `do_trade` поднимает `Refused`, автопилот ставит ALARM, хотя книга уже изменена. Это порождает ложный операционный исход и ручное вмешательство поверх состоявшегося ролла.

   **Ложное доказательство:** `live/contour_test.py` утверждает для того же U26 на `2026-09-10` одновременно навёрстывание и `not miss.refusals`. По показанному коду это утверждение пройти не может. Следовательно, сообщение «ВСЕ ПРОВЕРКИ ПРОЙДЕНЫ» относится не к этим файлам либо прогон не исполнялся как заявлено.

6. **ВЫСОКИЙ — `live/contracts.py`, `mismatches`: ISIN фондов проверяется только при генерации, но не при торговле.**  
   `row['isin']` вообще не сравнивается с `ContractDetails.secIdList`. `feed.contract_of` и `IBBroker._contract` называют этот общий предикат проверкой личности, хотя он проверяет только тикер, валюту, площадку и прочие поля. Денежный путь: реестр подменён/устарел и conId указывает на другую листинговую линию с тем же `localSymbol` и площадкой; сборщик получает её цену, а адаптер затем торгует её же — обе проверки согласованно проходят, но куплен не тот фонд. Это прямое ложное доказательство личности ETF.

7. **ВЫСОКИЙ — `live/signal_update.py`, `_commit_levels`: контрольный сайдкар переписывает прошлые эталонные уровни текущими данными поставщика.**  
   После допуска 0,1% выполняется безусловное:
   ```python
   rows.setdefault(d, {})[sym] = float(v)
   ```
   для всех доступных исторических месяцев. Значит база сравнения не фиксирована: поставщик может сдвигать историю на 0,09% при каждом запуске, а сайдкар каждый раз принимает новый уровень за эталон. Через несколько запусков накопленный дрейф становится большим, но ни одна отдельная сверка не нарушает порог. Денежный путь — изменение знака `close > SMA`, включение или выключение целой ноги. Утверждение «дрейф ловится сверкой уровней» ложно для постепенного пересчёта истории.

8. **ВЫСОКИЙ — `transition.py`, `_live_margins`: несколько серий одного корня схлопываются выбором последней, а не консервативным максимумом.**  
   ```python
   out[root] = float(...)
   ```
   При наличии ESU26 и ESZ26 результат зависит от порядка JSON. Денежный путь: следующая серия имеет меньшую маржу и затирает повышенную маржу удерживаемой серии; `preflight_margin_orders` завышает cushion и разрешает переход, который не выдерживает фактического требования. С учётом того, что `first_connect` пишет обе серии, дефект активируется штатным обновлением реестра.

9. **СРЕДНИЙ — `live/autopilot.sh`, `run_trade` и `run_close`: состояние дня определяется подстрокой вывода вопреки ненулевому коду.**  
   Любая ошибка, чей совокупный вывод содержит `не новее`, помечается `traded-$day`; аналогично любой вывод с `уже замкнута` помечается `closed-$day` и запускает backup. Денежный путь: программа сначала печатает эту фразу, затем падает на сверке брокера/состояния; автопилот подавляет повтор и считает обязательную операцию завершённой. Это именно класс ложного доказательства по тексту сообщения, а не структурному исходу.

10. **СРЕДНИЙ — `live/autopilot.sh`, команды `trade` и `close`: ручные точки входа обходят календарь, окна, ALARM и месячное обновление сигнала.**  
    Ветка `trade)` вызывает непосредственно `ensure_gw && run_trade`; она не проверяет `is_trade_day`, торговое окно маршрута Е, существующий ALARM и `sigup-$mon`. Денежный путь: операторский или внешний служебный вызов в 15:00 Чикаго на маршруте Е отправляет GTC на закрытую европейскую биржу либо торгует первым месяцем без запуска `signal_update.py`. Комментарии об обязательных воротах относятся только к `tick`, но интерфейс предоставляет обход этих ворот.
